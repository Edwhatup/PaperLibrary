您好！今天我们来聊一篇很有意思的论文，标题叫做 Program-as-Weights：一种模糊函数编程范式。这篇论文要解决的核心问题是：很多日常编程任务，比如从海量日志中筛选出关键信息、修复格式错误的 JSON 文件、或者根据用户意图对搜索结果进行排序，这些任务很难用传统的、基于精确规则的代码来实现。

过去，大家遇到这类“模糊”的任务，往往会求助于大型语言模型（LLM）的 API。比如，直接调用 GPT 模型来提取答案或者完成某个复杂的文本处理。这种方式虽然方便，但缺点也很明显：它依赖远程服务，每次调用都要付费，而且结果可能不稳定、难以复现，因为模型提供方可能会在不通知的情况下更新模型。更重要的是，它让我们的软件无法独立运行，总是要依赖外部服务。

为了解决这些痛点，这篇论文提出了一种全新的编程范式，叫做“模糊函数编程”（fuzzy-function programming）。它的核心思想是：把一个用自然语言描述的模糊函数，编译成一个紧凑的、可以在本地独立执行的神经网络“程序”。他们把这种方法称为 Program-as-Weights，简称 PAW。

PAW 的工作流程可以分为三个清晰的步骤：首先，开发者用自然语言描述他们想要实现的功能，这就像写一个函数说明书。接着，一个神经网络“编译器”会把这个自然语言描述，转换成一个轻量级的神经网络“二进制文件”，也就是一个小的、专门用于这个任务的模型适配器。最后，一个预先安装在用户设备上的、轻量级的神经网络“解释器”，会加载并运行这个“二进制文件”，就像执行一个用户自定义函数一样。

这样一来，大型语言模型就从一个“每次输入都解决问题”的角色，转变为一个“一次性构建工具”的角色。也就是说，你只需要在定义函数时调用一次大型模型进行编译，它就会生成一个很小的、可重复使用的程序。这个程序后续在每次函数调用时，都可以在本地快速、廉价地运行，而且完全离线。

PAW 程序本身是一个混合体，它包含两个部分：第一个是一个自然语言的“伪程序”，它其实是用户原始描述的一个清晰复述，可能还会包含一些输入输出示例。第二个部分是一个参数高效微调（PEFT）模块，比如 LoRA 适配器。这个模块会专门针对当前的任务，对固定的解释器模型进行重新调优。论文中解释说，离散的伪程序可以帮助解释器抵御原始描述中的拼写错误和歧义，而连续的 PEFT 模块则提供了仅靠文本无法实现的精细行为控制。

整个编译流程分两个阶段，都由一个 4B 参数的 Qwen3 模型来完成。第一个阶段是“伪编译器”，它是一个现成的模型，不需要额外训练。它通过一个小的任务重写模板，把用户原始的模糊描述转换成一个干净的伪程序，这个伪程序包括一个复述的任务描述和一些输入输出示例。第二个阶段是“LoRA 编译器”，这个才是论文中专门训练的模型。它读取用户的原始描述和前面生成的伪程序，然后生成 LoRA 适配器。为了训练这个 LoRA 编译器，研究团队发布了一个名为 FuzzyBench 的大型数据集，包含了 1000 万个示例，涵盖了 800 多个类别的模糊文本任务，比如分类、格式转换、解析、模糊匹配等等。

PAW 系统的效果非常显著。他们使用一个 0.6B 参数的 Qwen3 模型作为解释器，执行 PAW 程序。结果显示，PAW 程序的性能甚至超越了直接调用 32B 参数的 Qwen3 模型进行提示（准确率从 68.70% 提高到 73.78%）。更令人惊叹的是，PAW 系统在推理时所占用的内存大约只有直接提示方式的五十分之一。经过量化之后，它甚至可以在 MacBook M3 上以每秒 30 个 token 的速度运行，只需要一个 430MB 的共享基础模型，再加上每个程序 23MB 的 LoRA 适配器。如果使用更小的 GPT-2 路径，甚至可以完全在浏览器中通过 WebAssembly 运行。

这篇论文认为，Program-as-Weights 是迈向“小模型未来”的重要一步。在这个未来中，繁重的工作在编译时一次性完成，而软件的日常运行则在本地进行。论文还通过五个具体的案例研究，展示了 PAW 的应用潜力，包括事件驱动的日志监控、基于意图的网站导航、模糊搜索结果重排序、智能体预处理（在 ToolCall-15 任务上达到 93% 的准确率），以及一个多语言猜词游戏。这些都是那些难以用符号规则实现，但又不需要每次输入都调用 30B 参数模型 API 的模糊任务。

更有趣的是，PAW 范式还展现了跨模态的通用性。他们仅仅替换了文本编译器，换成了一个视觉语言模型（VLM），而解释器保持不变，PAW 程序就能处理图像相关的模糊任务。这意味着，图像的条件信息完全被编码到了编译器生成的 PEFT 模块中，而小型的文本解释器本身并不会直接处理图像像素。

总结一下，PAW 范式将模糊函数定义为可学习的权重，通过编译将自然语言描述转化为本地可执行的神经网络程序。这使得大型模型从解决具体问题转变为构建工具，实现了高效、本地化、可复现的模糊函数实现。

接下来，我们深入探讨一下 PAW 范式的核心技术细节。

PAW 的基本理念是，对于那些通过自然语言、示例或约束来描述比通过符号代码更自然的模糊函数，我们不应该每次都反复调用一个大型语言模型去近似它，而是应该编译出一个专门的“神经程序”，让一个固定的模型来执行这个模糊函数。

形式上来说，如果用户提供了一个自然语言的函数描述，可能还附带了一些输入输出示例，那么这个神经“编译器”就会把这些信息映射成一个“程序”。然后，一个小型且固定的神经“解释器”会加载这个程序，并根据输入生成输出。

这种“编译-解释”的结构，很像传统的编程语言：编译器将源代码翻译成可执行文件，然后运行时环境执行这个文件。但关键区别在于，这里的“可执行文件”是一个学习到的参数集合，而“运行时环境”是一个神经网络。解释器不需要重新训练，每当需要一个新的模糊函数时，只需要编译一个新的程序就可以了。

论文中提到，这个程序可以被视为一个单一的连续对象，但在他们具体的实现中，它是一个离散和连续组件的混合体。离散组件是一个可变长度的 token 序列，作为“伪程序”的一部分，提供给解释器作为输入。连续组件则是一个 PEFT（Parameter-Efficient Fine-Tuning）模块，比如一个注入到解释器中的 LoRA 适配器。

为什么要强调“程序”这个概念呢？因为这决定了生成物的用途。一个编译好的 PAW 程序是一个单一的文件，例如，对于 0.6B 参数的解释器，它的大小只有 23MB，再加上一个一次性的共享基础模型。这个文件可以被保存、版本控制、通过包管理器分发，并且可以通过两行代码的 API 在 Python 或 JavaScript 中调用。PAW 程序就像 Python 模块一样，有名称和版本，但它们的行为不是编码在源代码中，而是编码在权重中。编译器负责繁重的工作，而解释器则是一个固定的运行时环境，类似于传统软件栈中的 CPU 或字节码解释器。

现在我们来详细看看这个编译器-解释器系统是怎么设计的。

PAW 管道包含三个核心组件，它们都不依赖于程序形式选择的特定 PEFT 方法。

第一个是“伪编译器”（Pseudo Compiler）。它的作用是读取用户的模糊函数描述，并生成一个离散的“伪程序”。这个伪编译器是一个现成的 Qwen3-4B-Instruct-2507 模型，研究人员没有对其进行任何训练。给定用户描述，他们会用一个小的任务重写模板来提示这个模型，要求它生成一个清晰的任务复述，以及一些具有代表性的输入输出示例。这个输出就是程序中的离散组件。早期，他们尝试过用强化学习来训练一个编译器生成这个离散组件，但发现无论初始提示如何，编译器最终都会收敛到这种“复述加示例”的格式，所以他们干脆直接通过手动设计提示来让现成模型生成这种格式，从而省去了强化学习阶段。这个伪编译器在两种 PEFT 实现中都是共享的。

第二个是“PEFT 编译器”（PEFT Compiler）。它读取用户的原始描述和前面伪编译器生成的伪程序，然后从其隐藏状态中生成一个小型且参数高效的 PEFT 模块。论文中主要介绍了两种 PEFT 模块的实现方式：前缀调优（prefix-tuning）的 KV 缓存和 LoRA。其中，LoRA 是他们目前效果最好的方案。

我们先重点说一下 LoRA 编译器。LoRA 编译器是另一个 4B 参数的 Qwen3 模型，它和伪编译器一样，都是从同一个检查点初始化的，但这个 LoRA 编译器是经过训练的。给定用户描述和伪程序，LoRA 编译器会对其进行一次前向传播，输入是原始描述、伪程序，再加上一个固定序列的、经过学习的“前缀”token。然后，它会从 LoRA 编译器的不同层（均匀分布，每层对应解释器的一层）提取前缀位置的隐藏状态，并将它们堆叠成一个张量，这个张量会输入到一个叫做 LoRA 映射器（LoRA Mapper）的小型参数高效模块中。

LoRA 映射器是 LoRA 编译器的核心。它将 LoRA 编译器的隐藏状态转换为每个示例的 LoRA 权重。对于解释器中的每种目标模块类型（比如注意力层的 QKV 投影和 MLP 层），映射器都维护一组共享的可学习基。这些隐藏状态会先在深度对齐的层和前缀位置上进行平均池化，然后通过一个浅层 MLP 主干网络，最后投影成每个层、每个模块类型和每个基索引的混合系数。最终，通过这些混合系数和共享基，生成特定层和模块的 LoRA 权重。论文中使用了 rank 为 4，每种模块类型有 4 个共享基，应用于所有层和模块类型。这样，每个模糊函数大约会向解释器注入 38.5M 的 LoRA 参数。他们尝试了更复杂的 LoRA 映射器设计，比如按位置聚合、按层基等，但发现最简单的共享基设计效果最好。

第三个是“解释器”（Interpreter）。它是一个冻结的语言模型。为了执行一个 PAW 程序，解释器会首先将前面生成的 LoRA 适配器附加到其相应的目标模块上。然后，它会将伪程序的内容预先添加到用户输入的前面，最后自回归地生成输出。由于解释器是冻结的，并且 LoRA 适配器可以即时热插拔，因此一个设备上的解释器可以服务无数个 PAW 程序，实现“一个运行时，多个程序”的架构。

作为对比，论文也提到了前缀调优（Prefix-tuning）的实现方式。前缀编译器同样是一个经过训练的 4B Qwen3 模型。它生成前缀位置的隐藏状态，但不是转换成 LoRA 权重，而是通过一个小的线性映射器，将这些隐藏状态逐位置地投影成 KV 对。这些 KV 对会被预先添加到解释器注意力机制的 KV 缓存中，就像标准的前缀调优那样。解释器在运行时，其冻结的注意力机制就会将这些额外的 KV 对视为可见，从而影响输出。

在受控的对比规模下（相同的训练计算量），前缀调优的实现达到了 50.4% 的精确匹配率，而 LoRA 实现达到了 56.5%（rank=4 时）和 65.7%（rank=16 时）。两者都显著优于没有编译器的直接提示基线（9.8%）。显然，LoRA 是一种更强的 PEFT 方法，也是后续实验中全面扩展的实现方式。

接下来，我们看看训练过程。

整个 PAW 系统中，只有 PEFT 编译器是需要训练的。伪编译器是现成的、冻结的，解释器也是冻结的。PEFT 编译器被训练的目标是，生成一个 PEFT 适配器，当这个适配器和固定的伪程序一起注入到冻结的解释器中时，能够最大化目标输出的似然性。由于解释器和伪编译器都是冻结的，这实际上就简化成了一个监督学习目标。

训练目标函数很简单：对于每个训练三元组（规范、输入、目标输出），它会查找预先生成的伪程序，通过 LoRA 编译器进行前向传播以获取前缀位置的隐藏状态，然后将这些隐藏状态通过 LoRA 映射器得到 LoRA 权重，最后将这些权重注入到解释器中。损失函数是目标输出在冻结解释器下的负平均 token 对数似然。梯度会通过冻结的解释器反向传播到 LoRA 映射器，再从 LoRA 映射器反向传播到 LoRA 编译器的隐藏状态。

为了训练这个系统，研究团队构建了一个名为 FuzzyBench 的大型数据集。这是 PAW 风格方法训练中的一个关键障碍，因为之前没有公开的、针对“从规范编译模糊函数”任务的数据集。FuzzyBench 包含了 1000 万个示例，每个示例都是一个三元组：（规范、输入、目标输出），这些数据都是使用 gpt-5.2 生成的。

数据集的构建分为两个阶段。第一阶段，他们提示 gpt-5.2 生成模糊函数的自然语言规范。每次提示会生成八个规范，并通过不同的类别约束重复调用，以覆盖开发者实际遇到的模糊任务的广度。第二阶段，对于每个规范，他们再次提示 gpt-5.2 生成八个输入/输出对。规范按 80/10/10 的比例划分为训练/验证/测试集，这样测试集中的规范在训练时是完全未见的。为了进行评估，他们构建了一个经过验证的测试集，在这个测试集上，一个独立的、强大的模型（gpt-5-mini）和 gpt-5.2 在输出上必须达成一致，从而排除目标本身模糊不清的示例。

FuzzyBench 的构建是增量式的，通过 29 个版本逐步完成，每个版本都增加了 10 万到 50 万个示例，涵盖了新的模糊任务系列。最终的 1000 万个示例被分为七个高级任务家族，涵盖了开发者在模糊逻辑中实际遇到的各种任务，从原始文本处理、解析到智能体工具使用、网络智能、代码和命令生成以及安全/验证等。

为了评估系统的鲁棒性，他们还发布了测试集的噪声扰动版本，沿着八个维度进行了扰动：拼写错误、语法错误、歧义、格式漂移、所有噪声（组合）、简洁措辞、随意措辞和释义。每个维度都有三个强度级别（轻度、中度、重度）。

数据生成模型 gpt-5.2 本身达到了 96.09% 的准确率，gpt-5-mini 达到了 91.87%。这些数字为任何在此数据上训练的编译函数设定了性能上限。

现在我们来看看主要的实验结果。

研究团队将 PAW 与三类基线进行了比较，所有基线都在与 PAW 相同的测试集上进行评估。

第一类是直接提示（Direct prompting），包括开源的 LLM（Qwen3 0.6B、4B、8B、14B、32B；OLMo3-7B；gpt-oss-20B），以及两个作为经验上限的 API 模型（gpt-5-mini 和 gpt-5.2）。

第二类是符号代码生成（Symbolic code generation），采用了 ALCHEmist 的“LM-to-code”管道。这个方法是让一个强大的 LLM 编写 Python 代码来解决模糊任务，然后在推理时执行这些代码。

第三类是基于相同 0.6B 基础模型的标准适配方法，包括对 0.6B Qwen3 解释器进行 1 到 4 个 epoch 的完全微调，以及使用固定（非编译器生成）的 LoRA 适配器，rank 分别为 4、8、16。

主要结果显示，一个 0.6B 参数的解释器执行 PAW 程序，在 FuzzyBench 上达到了 73.78% 的精确匹配率。这超越了直接提示 32B 参数的 Qwen3 模型（68.70%），同时推理内存使用量大约减少了 50 倍（bf16 精度下，PAW 为 1.2 GB，而 Qwen3-32B 为 60 GB）。

在跨解释器扩展性方面，他们测试了 GPT-2 124M、Qwen3 0.6B 和 Qwen3.5 0.8B 三种解释器。结果发现 Qwen3 0.6B 是最强的解释器，而 Qwen3.5 0.8B 略弱。尽管 GPT-2 124M 参数量只有 Qwen3 0.6B 的五分之一，并且没有经过指令调优，它仍然能达到 54% 的准确率。这表明编译器生成的 LoRA 适配器即使在非常小、能力较弱的基础模型中，也能编码出可用的任务适应性。

PAW 范式还展现了无需更改解释器的多模态泛化能力。他们仅仅将文本编译器（Qwen3-4B-Instruct）替换为同系列的视觉语言模型编译器（Qwen3-VL-4B），而解释器保持不变，仍然是 Qwen3 0.6B，并且复用了相同的 LoRA 映射器。这意味着，图像条件信息完全被编码在 VL 编译器发出的 PEFT 模块中，小型的文本解释器本身并不会直接处理像素。

实验结果显示，PAW（LoRA）在三个 CoSyn 图表理解任务（化学、电路、音乐）上，均优于所有基线 VLM 模型（最高 4B 参数），例如在电路任务上达到 0.274，而最佳基线为 0.196。但在长格式结构化生成任务 Im2LaTeX 上，PAW（LoRA）的表现弱于其前缀调优的先行版本（0.181 对 0.391）。通过消融实验发现，这种差距是因为伪程序中长输入/输出示例占据了小型解释器有限的上下文预算。

接下来，我们看看一些消融实验。

关于 LoRA 映射器的架构变体，研究团队尝试了几种理论上比默认设计（对前缀 token 进行平均池化，浅层主干网络，共享基）更具表达力的变体。但结果是，每种变体都表现更差。最简单的设计，即将前缀 token 的隐藏状态平均池化成一个向量，运行一个单一的残差 MLP，然后投影到共享基集的混合系数，效果最好。他们没有给出明确的理论解释，但报告了这一发现，以供未来研究参考。

在“有编译器与无编译器”的对比中，PAW 与三个基于相同基础模型的“无编译器”基线进行了比较：对 0.6B Qwen3 解释器进行完全微调，以及在三个 rank 下的每任务固定 LoRA 适配器。使用相同的数据、相同的基模型、相同的训练预算，唯一的区别是是否移除了编译器。结果显示，PAW 超越了完全微调 15.4 个百分点，超越了最强的固定 LoRA 21.7 个百分点，这证明了性能提升确实来自于编译器生成的 LoRA。

这些消融实验表明，PAW 的性能提升并非仅仅因为使用了 LoRA 或微调，而是编译器能够根据模糊规范动态生成高效的 LoRA 适配器，这是关键所在。

在对噪声规范的鲁棒性方面，开发者编写的实际规范往往包含拼写错误、歧义和语法错误。研究团队在七个噪声维度（拼写错误、语法、歧义、格式、所有噪声组合、简洁措辞、释义）上，评估了 PAW 在噪声扰动测试集上的表现。

结果显示，PAW 在重度噪声下性能仅略有下降。这是为什么呢？研究人员假设这种鲁棒性是通过离散伪程序实现的：4B 参数的编译器在小型解释器看到原始规范之前，会将其转换为一个干净的复述，从而起到去噪的作用。为了验证这个假设，他们训练了一个绕过伪程序、直接将原始规范输入给解释器的变体。结果证实了这一假设。在干净输入上，提供伪程序只比直接输入原始规范好 1.6 个百分点。然而，在重度拼写错误的规范上，差距扩大到 4.5 个百分点。这说明，编译器作为一个 4B 参数的语言模型，其主要任务就是读取模糊规范并生成一个干净的复述，有效地对小型解释器所看到的输入进行了去噪，因此 PAW 在原始规范被破坏时性能下降很小。

除了基准测试，为了让 PAW 实际可用，研究团队还构建了一个开发者界面。一个 PAW 程序是一个单一文件，可以下载、缓存，并通过一个小的 Python 或 JavaScript API 调用。调用 paw.compile(prompt) 会将规范发送到编译器服务，并返回一个可序列化的程序对象；paw.function(id_or_path) 会加载一个编译好的程序，并将其作为 Python 可调用对象暴露出来。在第一次下载之后，所有执行都发生在本地，无需任何外部 API 调用。

在本地执行方面，为了实现设备上的运行，需要尽可能小的占用空间。他们将共享的解释器基础模型和每个程序的 LoRA 适配器都量化为与 llama.cpp 兼容的 GGUF 格式。结果显示，一个 4 位量化的基础模型（484MB）加上一个 4 位量化的 LoRA 适配器（每个程序 23MB），相对于 bf16 精度只损失了 1.3 个百分点。而一个 5 位量化的基础模型加上一个 5 位量化的适配器，在统计学上与 bf16 精度几乎没有区别。

在 MacBook M3 上的延迟测试显示，使用 Metal 加速时，4 位量化的基础模型加上 4 位量化的适配器，可以达到每秒 31.6 个 token 的速度，冷启动时间为 0.48 秒。

最后，我们回顾一下论文中提到的五个案例研究。

第一个是事件驱动的日志监控。这个应用取代了传统终端监控中基于等待的朴素方法，使用一个本地分类器，只在真正重要的日志行上触发警报。例如，它可以将“loss=0.05”这样的普通日志标记为 QUIET，而将“[Checkpoint] Saved model”或“Traceback”标记为 ALERT。

第二个是基于意图的网站导航。它为网站提供了一个自然语言的快速查找功能，而无需每次请求都调用 LLM API。例如，用户输入“how do I get started”，PAW 程序会将其分类为“docs”（文档）；输入“browse community programs”，则分类为“hub”（社区中心）。整个流程由五个 PAW 函数组成，每个函数都编译迅速，运行毫秒级。

第三个是语义搜索结果重排序。它将意图感知的模糊搜索功能添加到一个现有的关键词索引中，同样避免了在请求路径中放置 LLM。关键词搜索返回前 10-20 个候选结果，PAW 重排序器根据查询对每个结果进行评分（例如：exact_match, highly_relevant, somewhat_relevant, not_relevant），然后按分数降序返回候选结果。

第四个是工具调用流水线。一个包含 10 个 PAW 函数的流水线在 ToolCall-15 任务上达到了 93% 的准确率，捕获了通常只有大型模型才能实现的工具路由行为。这些 PAW 函数包括判断是否需要工具、工具路由、不可能检查、第二工具调用，以及六个参数提取函数（例如提取位置、股票代码、单位、搜索查询、人物、翻译内容）。日期/时间解析由正则表达式处理，OpenAI 的 tool_calls JSON 由确定性 Python 构建。

第五个是多语言猜词游戏。这是一个模糊的互动游戏，每个玩家的回合都由一个 0.6B 参数的 PAW 解释器在一个小型服务器上提供服务，每种语言对应一个 PAW 程序。LLM 只在编译时被调用，这使得这类游戏的托管成本非常经济。例如，输入“furry animal that meows and purrs”，PAW 程序会猜出“cat”。

这些案例研究充分展示了 PAW 范式在实际应用中的巨大潜力，它能够以低成本、高效率的方式，在本地解决各种模糊编程任务。

最后，我们来总结一下这篇论文的贡献和启发。

Program-as-Weights 提出了一种全新的编程范式，它将模糊函数一次性编译成一个小的神经二进制文件，然后在固定的解释器上本地执行。这意味着大型语言模型不再是每次输入都解决问题的“问题解决者”，而是每次函数定义时构建工具的“工具构建者”。这种转变不仅显著降低了推理成本和内存占用，还提高了本地执行的速度和可复现性。

PAW 的关键创新在于其“编译器-解释器”架构，特别是混合程序的概念，即结合了离散的伪程序和连续的 PEFT 适配器。伪程序负责去噪和提供清晰的任务描述，而 PEFT 适配器则提供精细的行为控制。FuzzyBench 这样一个大规模、高质量的合成数据集的发布，也为未来相关研究提供了宝贵资源。

PAW 范式在多模态任务上的泛化能力也值得关注，仅仅更换编译器就能处理图像相关的模糊任务，这表明其抽象的通用性很强。通过量化和本地执行优化，PAW 使得在消费级设备上运行复杂的模糊函数成为可能。

这篇论文为我们描绘了一个“小模型未来”的愿景：大型模型负责一次性编译生成精炼的、任务专用的神经程序，而小型模型则作为高效的本地运行时环境，执行这些程序。这对于开发者来说，意味着可以更经济、更自主地构建和部署那些需要处理模糊逻辑的应用程序，而不再受限于昂贵的远程 API 调用和不稳定的服务。对于我们自己的研究工作，PAW 提供了一个全新的思路：当面对那些难以用传统规则精确定义的任务时，我们或许可以考虑将任务描述“编译”成一个轻量级的神经模块，然后在本地快速运行，而不是每次都依赖大型模型的远程推理。
