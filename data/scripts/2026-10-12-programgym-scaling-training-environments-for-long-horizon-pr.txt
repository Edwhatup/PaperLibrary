好的，没问题。这是一段约 20 分钟的连续口播稿，将这篇论文的核心内容深入浅出地讲解出来，语速适中，适合开车时收听。

咱们今天来聊一篇很有意思的论文，叫做 ProgramGym：它主要解决的问题，是怎样为那些能够从零开始、像软件工程师一样构建程序的智能体，提供一个可扩展的训练环境。

现在啊，我们看到的很多编程智能体，它们通常处理的是两种任务：一种是“问题解决”，比如说给它一个现有的代码库，再给它一个 Bug 报告或者一个新功能需求，让它去打补丁、去修改。这就像 SWE-bench 这样的基准测试。另一种是“代码库生成”，也就是给它一份需求文档，让它从头生成一个完整的代码库，比如 NL2Repo-Bench。这两种场景，智能体要么是从一个已经存在的代码库出发，要么是从一份详细的需求文档出发。

但是，真正的软件工程师在从零开始构建一个程序的时候，往往不是这样的。他们会不断地探索“到底需要什么”，然后自己去设计“系统应该怎么实现”。这个过程，才是从无到有的、更像人类软件工程师的工作模式。

为了模拟这种“从零开始”的场景，学术界提出了“程序复现”任务，比如 ProgramBench。它的要求是：给智能体一份程序的使用文档和一个“参考程序”（但智能体看不到它的源代码，也不能联网），智能体需要根据文档和对参考程序的探索，来重建一个功能上一致的程序。这里面最关键的是，智能体需要自己去发现程序的行为，并从头设计实现方案。

目前的问题是，现有模型在 ProgramBench 上的表现非常差，甚至在最初的评估中，没有一个模型能完全解决任何一个任务。这说明，我们急需一个可扩展的、可验证的训练环境，能够提供可靠的行为监督，来训练这些“从零开始”构建程序的智能体。现有的那些“问题解决”任务的环境，比如 SWE-Gym，并不能提供这种行为监督。而像 MindForge 这样的尝试，虽然也涉及到程序复现，但它训练时并不验证智能体复现出来的程序功能是否正确，导致功能不正确的复现也可能被当作成功案例。

所以，这篇论文就提出了 ProgramGym 框架，它由两大部分组成：Program-Env 和 Program-Agent。ProgramGym 的目标，就是解决在构建可验证训练环境和支持智能体进行长周期开发过程中遇到的两大挑战。

第一个挑战是：“如何扩展可验证的训练环境？”你想啊，要构建参考程序的可执行文件和运行时沙箱，就得适应各种代码库特定的工具链和依赖项。每个代码库的构建方式都不一样。而且，生成的黑盒测试用例，既要能覆盖程序的多样化功能，又要能准确判断智能体复现的程序是否正确。如果一次测试生成不够好，可能会漏掉关键行为，或者断言不够强，不足以检测错误的实现。

第二个挑战是：“如何支持智能体的长周期开发？”我们知道，通用的智能体工具虽然支持工具使用，但它们本身并不能很好地协调探索和实现过程。智能体可能会在充分探索参考程序之前就开始实现，或者随着上下文窗口的增长，它会“忘记”之前观察到的需求。为了解决这些风险，智能体需要一个明确的开发工作流程，能够保留行为证据，并协调实现、审查和修订这些步骤。

ProgramGym 就是为了应对这些挑战而设计的。具体来说，Program-Env 通过一个“反馈驱动”的循环来构建可验证的训练环境。这个循环会修复运行时沙箱的构建问题，并提升黑盒测试用例的质量。通过这个新颖的流程，Program-Env 成功构建了覆盖 C、C++、Go 和 Rust 四种语言的训练环境。

而 Program-Agent 呢，它结合了“分析、实现和审查”这种角色隔离的工作流程，并引入了“版本管理”机制，用于编译检查和故障恢复。

我们先来详细说说 Program-Env 是怎么工作的。它的核心思想是利用通用的智能体工具（比如 Claude Code），但在此基础上增加反馈循环，来指导构建过程的修复和测试用例的优化。

Program-Env 首先会收集大量的候选代码库。它通过 GitHub 搜索 API 进行分层搜索，根据编程语言和星标数量来划分，并排除那些归档或分叉的代码库，还会进行元数据验证，确保许可证有效。最后，它会把每个代码库锁定到一个固定的提交版本，并检查是否有明确的构建配置文件。经过这一系列筛选，他们得到了三万多个候选代码库。

接下来是 Program-Env 的关键一步：可执行文件和沙箱的生成。对于每个符合条件的代码库，智能体需要生成两个脚本：一个是 download.sh，用于在线准备依赖项；另一个是 compile.sh，用于离线编译。这里为什么要分成在线和离线呢？因为在程序复现任务中，智能体生成代码后，编译时是不能联网的。所以，download.sh 必须把所有需要的工具链和依赖都下载好，配置好，确保 compile.sh 在没有网络的情况下也能成功编译。整个流程只有当这两个脚本都成功执行，并且生成的可执行文件通过“加载性检查”时，才算通过。如果失败了，诊断信息会返回给智能体，让它去修改脚本。这个通过验证的可执行文件就作为参考程序，而准备好的运行时环境就作为沙箱。

这个构建过程是相当严格的。它会先用一个静态代码检查器，确保生成的脚本不会隐藏错误。比如，它会拒绝那些使用 || true 这样的命令来掩盖失败，或者把错误输出重定向到空的文件里。然后，它会进行两阶段执行检查：首先，在有网络的环境里运行 download.sh，确保它能下载所有依赖；成功后，会记录导出的环境变量和安装的软件包快照，并把容器状态冻结，作为运行时沙箱。接着，把项目源代码放到一个独立的工作目录中，从沙箱启动一个禁用网络的容器，恢复之前记录的环境变量，然后执行 compile.sh。如果这个离线编译成功，并且可执行文件通过了动态链接检查，才算构建成功。

如果构建失败了，Program-Env 会把失败原因、诊断信息以及建议的修复方案，作为结构化反馈返回给智能体。比如，如果缺少某个依赖包，它会明确告诉智能体需要安装哪个包。智能体必须阅读这些反馈，然后才能修改脚本，避免重复犯错。这个反馈循环最多会尝试四次。

一旦构建成功，Program-Env 就会准备资源用于黑盒测试用例的构建。它会根据代码库的大小来决定并行分支的数量，并为每个分支分配一个功能模块。同时，它还会对可执行文件进行插桩，以测量代码覆盖率，并准备测试运行时环境。此外，它还会提取代码库的文档，比如 README.md，作为智能体复现时的参考文档。这些准备步骤都是并行运行的。

接着，Program-Env 的另一个核心功能是黑盒测试用例的构建。为了保证测试的可靠性，Program-Env 同样使用了结构化反馈，指导智能体迭代地扩展测试覆盖率，并增强断言的强度。

测试用例的构建是并行进行的，每个分支都会在 Claude Code 工具的辅助下，在一个外层循环中运行。每轮结束后，Program-Env 会将反馈组织成三部分：

第一部分是“总结”，记录了已经完成的工作、未解决的问题以及原因，这有助于在各轮之间保留上下文。

第二部分是“程序分析”，它会通过动态分析定位未覆盖的功能，并通过静态分析将其追溯到公共入口点。这能帮助智能体知道哪些功能还没被测试到。

第三部分是“验证”，这是最重要的一部分。它通过四种检查来筛选测试用例：
1. “通过检查”：验证测试用例是否能在参考程序上成功运行。如果连参考程序都跑不过，那这个测试用例肯定有问题。
2. “双重检查”：检测重复运行测试时是否出现不一致的结果，确保测试的稳定性。
3. “假人检查”：判断测试用例是否会接受一个“假人实现”（也就是一个什么都不做或者返回固定值的简单实现）。如果一个测试用例能被假人实现通过，说明它无法区分正确和不正确的实现，断言太弱。
4. “弱断言检查”：标记那些断言不足的测试用例。这可能是通过程序分析发现的，比如某个关键功能没有被断言覆盖。

这些检查帮助识别无效、不稳定或区分度不够的测试用例。在下一轮中，智能体就会读取这些处理过的文档，修复被标记的测试用例，然后再扩展覆盖到未探索的目标。当一个子智能体达到功能覆盖率阈值或达到轮次限制时，它就终止了。所有分支终止后，它们的测试套件会被合并并再次验证，Program-Env 只保留通过所有检查的测试用例。这样就确保了最终生成的测试套例是可靠的、高质量的。

Program-Env 最终成功构建了 1648 个训练环境，涵盖 C、C++、Go 和 Rust 四种语言，包括了开发者工具、命令行工具等八个功能类别。这些环境的平均代码覆盖率达到了 72.99%，总共产生了 665,512 个经过验证的测试用例。这说明 Program-Env 确实提供了一个可靠、多样且可扩展的训练环境。

讲完了 Program-Env，我们再来看看 Program-Agent。它主要是解决长周期开发中，智能体容易“失忆”和“跑偏”的问题。Program-Agent 的设计灵感来源于软件工程师的迭代工作流程。它结合了“角色隔离”的迭代工作流和“版本管理”机制。

Program-Agent 采用了“角色隔离”和“会话分离”的迭代范式。它将程序复现任务解耦成两个逻辑角色（分析师和实现者）和三个阶段：分析、实现和审查。每个阶段都在独立的会话中执行，这样可以避免不同阶段之间的内存污染，也就是防止上下文混淆。阶段之间的信息传递是通过“交接件”完成的，比如行为证据和阶段报告，而不是传递完整的对话历史。

第一个阶段是“分析阶段”。在这个阶段，分析师会阅读文档并探索参考程序，但它不能编辑工作区，这样能保证收集到的约束条件是无偏的。所有提取的行为证据和实现指南都会存储在一个只读的 analysis.md 文件中，供后续阶段使用。

第二个阶段是“实现阶段”。实现者根据分析阶段冻结的交接件，在一个独立的会话中开发候选程序。这里同样不能访问参考程序，以避免上下文噪声。第一次迭代的目标是生成一个可编译的基线版本，以避免基本的编译失败。随后的几轮会逐步解决审查阶段发现的问题。所有的实现进度和代码更改都会记录在 implementation-k/delivery.md 中，以便进行明确的追溯。

第三个阶段是“审查阶段”。分析师会比较官方的参考程序和新构建的、不可更改的候选程序，并将所有经过验证的行为差异转换为可操作的修订要求，记录在 review-k/review.md 中。这里同样会强制执行严格的只读访问，防止智能体为了自圆其说而修改程序。

Program-Agent 还设定了明确的“迭代预算”，比如最多进行五轮实现。这解决了单会话工作流中常见的两个问题：一是过早终止，导致实现不完整；二是无限制的低价值探索，导致长周期复现不稳定。通过明确的迭代预算，Program-Agent 确保了智能体能够有条不紊地推进。

除了角色隔离的工作流，Program-Agent 还引入了“版本管理”机制。在多次实现迭代中，共享的工作区可能会积累错误编辑，直到 compile.sh 无法再生成可执行文件。为了避免这种情况，Program-Agent 将“独立编译”作为每个实现轮次的“关卡”。它会导出一个干净的源代码快照，并在开发工作区之外编译这个快照。如果快照成功生成了可执行文件，就会被存档到 Revisions 中，并转发给下一个审查阶段。

此外，如果某个阶段超时、缺少所需的交付件，或者编译失败，它会在有限的预算内重新尝试。如果重试仍然失败，实现会回滚到上一个经过验证的版本。一个成功的版本就会成为后续迭代的恢复检查点。这确保了多阶段复现过程的稳定推进。

接下来，我们来看看实验结果，看看 ProgramGym 的效果如何。

首先是 ProgramGym 的整体有效性。研究人员在 ProgramBench 上评估了 Program-Env 训练后的模型和 Program-Agent。他们发现，Program-Env 确实可以为从零开始的程序复现任务提供可验证的训练环境。在保持智能体脚手架（比如 Claude Code）不变的情况下，仅通过 Program-Env 轨迹进行训练，Qwen3.8-27B 模型的“测试通过率”从 34.87% 提高到了 42.84%。这个提升非常显著，甚至超过了旗舰模型 GPT 5.4 在 mini-SWE-agent 下的表现。这说明 Program-Env 提供的运行时沙箱和黑盒测试用例，为程序复现任务的训练提供了可靠的行为监督。

Program-Agent 也极大地扩展了模型在长周期程序复现任务中的能力边界。在模型权重不变的情况下，只改变智能体脚手架，Program-Agent 将 Qwen3.8-27B 的测试通过率从 34.87% 提高到了 55.71%，将 Qwen3.8-27B-SFT 的测试通过率从 42.84% 提高到了 56.25%。这两个结果都超过了旗舰模型 Claude Opus 4.7 和 Gemini 3.5 Flash 在 mini-SWE-agent 下的表现。这表明，Program-Agent 这种模拟软件工程师的工作流程，能够让同一个模型恢复更多的程序行为，比单会话的脚手架更有效。

不过，论文也指出，完全复现一个程序仍然非常困难。即使测试通过率能超过 50%，但“几乎解决”（通过 90% 以上测试）和“完全解决”（通过所有测试且没有作弊标记）的任务百分比仍然接近于零。旗舰模型在 mini-SWE-agent 下的完全解决率为 0%，即使经过 Program-Env 训练后，“几乎解决”的比例也从 3.50% 下降到了 1.50%。这说明，从零开始的整个程序复现任务仍然是一个未解决的难题。

在训练环境分析方面，Program-Env 成功构建了 1648 个任务，总耗费了 1367.7 亿个 token。这些环境涵盖了 C、C++、Go 和 Rust 四种语言，从小型工具到大型复杂项目都有。为了确保验证的可靠性，反馈循环迭代地扩展了覆盖率并完善了测试套件，平均覆盖率达到 72.99%，总共生成了 665,512 个经过验证的测试用例。这表明 Program-Env 确实提供了一个可靠、多样且可扩展的训练环境。

关于测试时迭代预算的影响，实验发现 Program-Agent 的性能可以随着迭代预算的增加而提高。他们用 Qwen3.8-27B-SFT 模型在 Program-Agent 下测试了不同迭代预算。结果显示，当迭代次数从 1 增加到 3 时，测试通过率从 43.49% 提升到 54.13%，当迭代次数达到 5 时，进一步提升到 56.25%。大部分的性能提升在 3 次迭代时就已经显现。这说明 Program-Agent 确实能在迭代预算增加的情况下，持续恢复程序行为。

最后，对智能体行为的分析表明，ProgramGym 主要通过 Program-Agent 来改变智能体的行为。在 Claude Code 下，无论模型是否经过 Program-Env 训练，智能体主要使用“执行”和“探测”这两种操作。但是，在 Program-Agent 下，智能体的“读取”和“Git 操作”显著增加，尤其是在经过 Program-Env 训练后。这说明 Program-Agent 将智能体的行为模式，从单纯的执行和探测，转变为了更多的探索和版本管理，使其更像一个真正的软件工程师。

总的来说，ProgramGym 框架为从零开始的长周期程序复现任务提供了一个强大的解决方案。Program-Env 通过反馈驱动的流水线，能够从各种代码库中构建出高质量、可验证的参考可执行文件、运行时沙箱和黑盒测试用例。而 Program-Agent 则通过角色隔离的工作流程和版本管理机制，帮助智能体进行系统化的长周期开发。这些创新使得智能体在程序复现任务上的表现得到了显著提升。

对我们听众的工作来说，这篇论文的启发是多方面的。

首先，它强调了“可验证环境”的重要性。在训练任何复杂的智能体，特别是涉及到代码生成和测试的场景时，仅仅生成数据是不够的，还需要一套严格的验证机制，确保数据的质量和可靠性。Program-Env 的反馈循环和多重验证机制，为我们构建高质量训练环境提供了具体的方法论。我们可以借鉴这种反馈驱动的思路，在自己的任务中设计类似的验证流程，比如在生成数据后进行多轮次的校验和修复。

其次，“长周期开发”和“上下文管理”是智能体面临的普遍挑战。Program-Agent 提出的“角色隔离工作流”和“版本管理”思想，对于设计任何需要多步骤、多轮次决策的智能体都非常有价值。将一个复杂任务分解为不同的、具有明确职责的阶段，并通过结构化的交接件进行信息传递，可以有效避免上下文污染和信息遗忘。同时，引入像 Git 这样的版本管理机制，确保每一步的进展都是可追溯和可恢复的，这对于提高智能体的稳定性和鲁棒性至关重要。

再者，论文也指出了当前智能体在“从零开始”构建复杂系统方面的局限性。即使经过 ProgramGym 的优化，完全复现一个程序仍然非常困难。这提醒我们，在设计和评估智能体时，要认识到现实世界的复杂性，并持续探索更有效的架构和训练方法。它也为我们指明了未来研究的方向，比如如何让智能体更好地进行高层次的系统设计和架构决策，而不仅仅是代码实现。

最后，ProgramGym 的开源，也为整个社区提供了一个宝贵的资源。我们可以基于它的环境和工具，继续推动编程智能体领域的发展，让它们能够真正像人类工程师一样，发现需求，设计系统，从零开始构建出复杂的软件。
