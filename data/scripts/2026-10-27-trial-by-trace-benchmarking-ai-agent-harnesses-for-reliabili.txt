目前，大型语言模型已经从简单的文本生成工具，发展成了能够执行复杂多步任务的智能体。这些智能体通过调用工具、执行指令、修改文件以及与外部环境交互，将用户的目标转化为具体的行动和可观察的结果。然而，一个人工智能智能体的表现，并不仅仅取决于其底层的大语言模型本身。它还高度依赖于支持其运作的“智能体线束”（Agent Harness）。这个线束负责连接模型与周围的各种组件，比如系统指令、上下文管理、可用工具、执行环境、持久状态、生命周期控制和安全机制。它决定了模型能接收到什么信息，能采取哪些行动，以及工具的执行结果、错误和状态变化如何呈现给模型。因此，即便使用相同的模型，通过不同的线束部署，其行为也可能大相径庭。然而，现有的大多数智能体基准测试，往往只关注模型的能力和智能体的整体任务完成度，却很少深入评估这些智能体线束的可靠性。

这意味着，一个任务的成功可能掩盖了线束层面上下文丢失、工具结果误导或生命周期违规等问题；反之，任务失败也可能发生在线束忠实执行其职责的情况下。仅仅通过最终结果来比较，我们很难找出究竟是线束的哪些行为导致了观察到的性能差异。这正是今天我们要深入探讨的这篇论文《Trial by Trace: Benchmarking AI Agent Harnesses for Reliability and Failure Attribution》所要解决的核心痛点。它提出了一套名为 TraceTrial-Bench 的全新基准测试，旨在从机制层面评估智能体线束的可靠性，并提供可审计的失败归因能力。

这篇论文的核心目标，就是将智能体线束视为一个独立的、对可靠性至关重要的组件来进行测试，而不是将其仅仅看作模型的一个透明包装器。为了实现这一点，TraceTrial-Bench 回答了三个关键问题：首先，智能体是否生成了所需的工件并执行了正确的动作；其次，原生线束是否保留了任务所需的信息、执行语义和生命周期行为；最后，观察到的智能体侧故障是否与预先声明的线束侧故障传播机制相符。

为了系统地评估线束的可靠性，研究人员首先基于现有的线束分类法，将可靠性划分为七个核心维度：上下文（Context）、执行（Execution）、治理（Governance）、生命周期（Lifecycle）、可观察性（Observability）、工具（Tools）和验证（Verification）。这七个维度涵盖了线束在整个智能体运作过程中所承担的各项职责。例如，“上下文”维度关注信息在不同会话或步骤中是否正确传递和隔离；“执行”维度则关注命令的实际执行结果和错误处理；“工具”维度评估线束如何暴露工具接口、传递调用和返回结果。这种细致的分类，使得评估能够精准地针对线束的特定机制而非泛泛而谈。

在此基础上，研究团队构建了九十五个专家级的、机制导向的任务。这些任务通过实际的工作流程来锻炼特定的线束机制，并且每个任务都配有明确的行为要求、智能体交付物以及可执行或基于状态的真实参考（ground truth）。这意味着，对于每个任务，我们不仅知道智能体应该做什么，还知道线束在背后应该如何支持。为了确保跨线束比较的公平性，他们设计了跨线束适配器。这些适配器在保持任务目标和评估标准一致的同时，允许每个线束保留其原生的接口和执行行为，从而实现语义等效的比较，避免因适配器引入额外功能或改变行为而影响评估结果。

接下来，我们来看看 TraceTrial-Bench 的核心技术模块。第一个是“轨迹追踪模块”（Trajectory Tracing，简称 TT）。这个模块负责捕获智能体的执行轨迹，并将其统一重构为一种共享的、名为“轨迹中间表示”（Trace Intermediate Representation，简称 Trace IR）的标准化格式。这就像是把不同品牌的汽车行驶记录仪的数据，都转换成一个统一的格式，这样才能进行横向比较。更重要的是，它在转换过程中会保留数据的来源信息，确保可审计性。由于不同的线束暴露的观测接口各异，轨迹捕获是通过源特定的适配器实现的。例如，针对 Codex 的适配器读取其 JSON 事件流，而 Claude Code 的适配器则结合流式 JSON 输出和会话记录。这种设计确保了能够兼容各种原生线束，同时进行统一的分析。

捕获到的轨迹事件被规范化为通用事件模式，每个事件都包含模式版本、序列号、时间戳、运行 ID 和事件类型等通用字段。对于工具交互，它会记录工具调用和相关的返回结果，包括错误状态、退出代码、持续时间等。这里一个非常重要的设计是“调用-结果关联和执行血缘关系”：它利用线束的原生调用标识符将工具结果与其调用关联起来，对于模糊或无法匹配的观察，则明确标记为未链接，而不是进行启发式配对，这保证了数据分析的严谨性。此外，它还会检查“提供者级别”的工具声明，直接从模型提供商的请求中提取结构化的工具声明，而不是仅仅依赖线束的静态配置，这使得对工具可用性的判断更加权威和准确。

第二个关键模块是“多源证据获取模块”（Multi-source Evidence Acquisition，简称 MEA）。由于完整的执行轨迹可能非常庞大且异构，直接将其全部提供给评估模型或人工审查是不现实的。MEA 模块的作用就是将这些轨迹记录、工作空间工件和权威环境状态结合起来，为特定的评估标准组装出有界限、有针对性的证据包。它区分了“存档证据”（用于审计）和“判决证据”（用于评估）。每个评估判据都会声明其所需的事件类型、字段、匹配条件以及返回记录的最大数量。例如，智能体层面的判据会选择与基线相比发生变化的文件工件，而线束层面的判据则会选择轨迹和探测证据。这种机制保证了评估的确定性和可检查性，同时避免了评估模型处理过多无关信息。

有了这些轨迹和证据，接下来就是“两层评估框架”。这个框架将评估过程分为两个独立的层面：智能体性能评估和线束可靠性评估。在任何语义评估之前，运行会先经过一个“准入关口”，检查其结果、配置、任务、模型和线束身份是否一致，生命周期和清理记录是否完整，轨迹和摘要是否被存档清单覆盖。只有通过准入检查的运行，才能进入语义评分阶段。

智能体层面的评估，主要检查智能体是否完成了所需的动作、是否符合任务要求以及最终交付物是否正确。它将智能体生成的文件工件与权威状态进行比对。线束层面的评估，则关注原生线束是否忠实履行了其信息传递和执行职责，例如上下文是否完整、工具调用是否正确、生命周期管理是否符合预期等。线束层面的评估会使用轨迹和探测证据。这两个判决向量是独立的，这意味着智能体任务成功并不自动意味着线束可靠，反之亦然。例如，论文发现，有百分之三十一点一的运行在至少一个线束判据失败的情况下，竟然成功完成了任务。这充分证明了将两者分开评估的必要性。

在评估过程中，判据被分为“确定性规则”和“语义判据”。确定性规则可以通过任务特定的验证器进行自动化检查，例如文件内容是否匹配预期。而语义判据则需要一个独立的“判官模型”（Judge Model）进行语义解释。判官模型在评估时会收到一个由 MEA 模块生成的、针对特定判据的证据包。所有判官模型的调用、响应、解析分数和理由都会被存档，以确保透明度和可审计性。最终的得分是两个层面通过判据数量的简单平均，但每个判据的二进制判决结果和归因信息都会被保留。

最后一个关键模块是“故障归因模块”（Failure Attribution，简称 FA）。这个模块旨在将观察到的智能体层面的故障，与线束层面的故障联系起来，并试图找出可能的因果链条。它将故障归因分为两个独立的问题：线束层面是否存在一个可支持的故障，以及智能体层面的故障是否遵循了针对该任务声明的机制。

归因过程从判据层面的判决结果开始。首先，它会定义线束侧的失败集合。需要注意的是，并非所有线束层面的零分都代表线束本身的缺陷。在某些情况下，智能体的一个动作可能会使目标属性变得不可观测，比如一个包装命令可能会用自己的退出状态覆盖被测试命令的退出状态。这些被绕过的判据虽然在分数报告中仍显示为零，但不会被计入归因分析的失败集合中，这使得归因更加精确。

在执行之前，每个任务都可以声明一个“候选机制链接”，表明一个线束判据的失败可能通过特定的中间信息、动作或状态扭曲，影响到某个智能体判据。当运行中同时出现这两个判据的失败，并且满足预设的激活条件时，这个候选机制链接就会被“激活”。但需要强调的是，一个激活的候选链接仅仅记录了声明的端点和激活条件在运行中存在，它并不能自动证明中间机制确实导致了故障的传播。

要将一个候选链接提升为“已验证的传播声明”，还需要进行人工审查。人工审查会确认两个端点的判决结果，将线束端点与该判据的权威证据源进行核对，并寻找在事件顺序上与声明机制一致的、可观察到的中间扭曲。审查还会考虑证据来源和可能的竞争性解释。只有经过这样严格的验证，才能确认为真正的故障传播。

通过这些模块，TraceTrial-Bench 能够为每次运行生成详细的记录，包括配置和来源信息、执行证据（如规范化和原生轨迹、提供者请求元数据、工作空间变化等）以及评估工件（验证器输出、判据特定证据、判官记录和分层分数）。这些输出为可审计的失败分析提供了坚实的基础。

在实验设置方面，研究团队评估了四种原生的智能体线束：Claude Code、Codex、DeepSeek Harness 和 OpenClaw。同时，他们使用了九种不同的模型配置，包括 DeepSeek-V4-Pro、Gemini 3.7 Flash、GLM-5.3、GPT-5.6-Sol 等主流模型。整个实验矩阵包含了九十五个任务与这四种线束和九种模型的全部组合，总计进行了三千四百二十次运行，每次运行都经过了精心选择和最终评估。所有的运行都在 Docker 容器中执行，并配有任务特定的工作空间、工具和资源限制。语义判官模型统一使用了 deepseek-v4-flash，确保了评估标准的一致性。

那么，实验结果揭示了什么呢？

首先，在所有三千四百二十次运行中，有百分之三十九点五的运行成功满足了所有的智能体判据，这代表了传统的任务成功率。然而，只有百分之八点四的运行同时满足了智能体和线束两个层面的所有判据。这个巨大的差距——从近百分之四十的任务成功率骤降到不足百分之九的两层都成功率——有力地证明了，仅仅关注任务完成度会掩盖大量的线束层面可靠性问题。

在整体分层结果方面，不同线束的表现差异显著。Claude Code 在智能体任务成功率上表现最好，达到了百分之四十四，并且在智能体宏观得分和综合得分上也位居榜首。然而，OpenClaw 在线束宏观得分和微观得分上表现最佳，分别达到了百分之七十二和百分之七十一点九，并且在“双层都干净”（即智能体和线束所有判据都通过）的运行比例上也最高。

这里有一个非常重要的发现：观察到任务成功率最高的线束，并非是线束判据满足度最高的线束。 这直接验证了论文的核心论点：单凭最终结果的评估，无法全面揭示线束的真实可靠性。线束宏观得分的范围从 Codex 的百分之五十九点八到 OpenClaw 的百分之七十二，有十二点二个百分点的差距，这表明不同线束在机制可靠性上存在显著差异。而智能体任务成功率的范围则相对较小，只有八点二个百分点。这进一步强调了线束可靠性评估的重要性，因为它揭示了传统评估可能忽略的深层差异。

论文还分析了故障交叉情况和候选链接激活。在所有运行中，百分之三十一点一的运行在至少一个线束判据失败的情况下，智能体任务却成功了。这正是我们之前提到的“任务成功掩盖线束失败”的典型案例。同时，有百分之四十六点九的运行至少有一个线束层面的零分，但智能体层面却没有任何零分，这被称为“操作性吸收状态”，意味着线束虽然存在问题，但智能体仍设法完成了任务。这表明线束的韧性或智能体在应对线束缺陷时的适应能力。

在故障归因方面，研究发现，在同时存在线束和智能体故障的运行中，约有百分之六十六点八的运行激活了至少一个候选机制链接。这意味着在大多数情况下，当智能体和线束都出现故障时，可以找到预先定义的、合理的故障传播路径。这为开发者深入诊断问题提供了有价值的线索。

这篇论文的局限性在于，它强调了激活的候选链接仅仅是记录了预设条件和故障的存在，但其本身并不构成因果结论，真正的因果传播还需要人工验证。此外，由于任务修订和恢复运行的存在，对于不同线束之间性能差异的因果解释也需要谨慎。

总的来说，TraceTrial-Bench 提供了一个可审计、可复现的基础，用于比较智能体线束、诊断其故障，并研究线束设计如何与模型行为相互作用。它的核心价值在于，通过引入机制导向的基准测试、精细的轨迹追踪、多源证据获取以及分层评估和故障归因框架，我们能够更深入地理解智能体系统的可靠性，而不仅仅停留在表面任务完成度上。对于我们的研究工作而言，这意味着在构建和评估人工智能智能体时，我们不仅要关注底层模型的强大，更要高度重视线束这个关键组件的可靠性。只有对线束的上下文管理、工具交互、生命周期控制等各个方面进行严格而系统的评估，我们才能真正开发出稳定、可靠、值得信赖的智能体系统。
