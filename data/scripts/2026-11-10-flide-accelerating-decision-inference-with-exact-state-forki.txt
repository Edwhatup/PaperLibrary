现有的大语言模型推理引擎，在面对一类特殊的工作负载时，会陷入一个非常尴尬的困境：要么重复计算大量相同的内容，要么为了避免重复计算而悄悄地修改了输入，导致输出结果发生偏移，甚至翻转决策。这篇论文要解决的，就是这个问题。

这类特殊的工作负载叫做决策模型推理。为了让你理解它和普通文本生成的区别，先解释一下背景。

我们平时用大模型生成文本，模型的输出是一段连续的话，一个字一个字地往后生成。但在很多实际系统里，大模型并不是用来写文章的，而是用来做判断的。比如：一个路由系统要决定这个用户的问题应该发给哪个下游模型；一个评分系统要判断这个回答质量如何；一个智能体在每一步行动之后，需要判断当前状态、决定下一步怎么走。这些场景里，模型只需要输出一个概率分布，表示对几个离散选项的置信度，不需要生成长文本。

为了高效完成这类任务，出现了专门的决策模型，论文里提到的代表是 Jev。这类模型通常会接收一段很长的上下文，比如一段对话历史或者一个智能体的完整轨迹，然后针对这段上下文回答多个问题，每个问题输出一个离散选项上的概率分布。

这里就出现了一个非常自然的结构：多个问题共享同一段上下文。逻辑上，这就像一棵树，树干是共享的上下文，每个问题是从树干分出去的一根树枝。最高效的做法是树干只算一次，然后每根树枝从树干末尾出发，各自往后算自己的部分。

但是现有的推理引擎做不到这一点，原因在于它们是为文本生成设计的，处理单位是一条线性序列。当你把多个问题送进去，它们会按照自己的逻辑各自处理，而不是按照这棵树的逻辑统一处理。

具体来说，现有引擎面对多问题请求时，大致有两种做法，各有各的问题。

第一种做法是把每个问题当成独立的序列单独跑。这意味着共享的上下文要为每个问题各自计算一遍，或者从前缀缓存里恢复一遍。对于纯注意力模型，前缀缓存的恢复效果还算可以。但对于混合架构的模型，比如 Qwen3.5 这类同时包含注意力层和循环层的模型，就麻烦了。循环层，具体来说是论文里提到的 Gated DeltaNet 层，把所有之前的 token 信息压缩进一个固定大小的循环状态矩阵里，这个状态只能在固定的块边界处保存，不能在任意位置恢复。所以每个问题不得不从最近的块边界重新计算，这段重复计算的开销相当可观。

第二种做法是把所有问题拼接成一条长序列，中间用分隔符 token 隔开，然后一次跑完。这叫做多项目评分，multi-item scoring，SGLang 实现了这个功能。表面上看，这样共享的上下文只算了一次，效率提高了。但问题出在分隔符上。每个问题在读取自己的内容之前，都会先读到前面的分隔符 token，这个额外的 token 会影响模型内部的隐藏状态，导致这个问题最终输出的概率分布，与它单独跑时的结果不一样。这不是微小的数值误差，而是系统性的偏移。论文里提到，在某些情况下，多项目评分的输出与 float32 参考结果的总变差距离，大约是 Flide 的十二倍，而且有高达 29% 的分类决策会因此被翻转。对于一个依赖概率置信度做决策的系统来说，这是不可接受的。

还有第三个问题，与上述两种做法都相关，是浮点数的不确定性。在动态批处理下，不同时刻到来的请求数量不同，GPU 执行矩阵乘法时的归约顺序会随之变化，浮点加法不满足结合律，所以同一个请求在不同服务器负载下可能得到不同的结果，同一个决策可能时而是这个选项时而是那个选项，这对生产系统来说是严重的可靠性问题。

论文作者把这三个问题归结为同一个根本原因：决策请求的逻辑结构是一棵树，但现有引擎的物理执行结构是一条序列，两者之间存在根本性的不匹配。

Flide 的核心思路就是把这两层结构解耦：逻辑上保持树形结构，物理上用一条扁平的 token 流统一执行。每个请求的树形依赖关系不写进 token 序列里，而是存储在 GPU 上的元数据里，让计算内核在执行时按照这份元数据来正确地访问和隔离各个分支。

这里有一个重要的设计动机值得细说。为什么一定要把依赖关系放在元数据里，而不是放在序列里？因为如果放在序列里，就得在序列中插入某种标记或分隔符，而任何插入的 token 都会进入模型的计算路径，污染每个问题看到的输入，就是多项目评分犯的错误。把依赖关系放在元数据里，序列本身就是干净的，每个问题看到的 token 序列和它单独运行时完全一致。

那么具体怎么做呢？先看物理布局。Flide 把一轮请求里所有的 token 拼成一条连续的流，不加填充，不加分隔符。对于每个请求，先放上下文的 token，再放每个问题的 token，依次排列。每个 token 携带三个元数据字段：它属于哪个请求、它属于哪个分支、它在自己序列里的位置。这份元数据全部住在 GPU 上，不经过 CPU 传递。

然后看注意力层的处理，这是论文称为 ForkAttention 的核心机制之一。在标准的注意力计算里，一个 query token 应该能看到哪些 key token？Flide 的规则是：只看同一个请求内的 token，而且只看共享上下文和自己所在问题分支的 token，不能看其他兄弟问题的 token。这用一个稀疏的注意力掩码就能实现，注意力层本身支持掩码操作，所以在纯注意力模型里，ForkAttention 相对直接。

但混合模型里有 Gated DeltaNet 层，这才是真正的难点。来解释一下这个层的机制。Gated DeltaNet 是一种循环层，它不保存所有之前 token 的 key-value 对，而是把所有历史信息压缩进一个固定大小的矩阵状态里，通过一个带门控的 delta 更新规则不断迭代。这意味着，当你在序列里往后走的时候，这个矩阵状态里已经混入了所有之前 token 的信息。如果两个问题共享一条序列，那么问题 B 在计算时，它的循环状态里已经包含了问题 A 的信息，这就彻底破坏了隔离性，注意力掩码在这里没有任何作用，因为根本没有注意力矩阵可以掩盖。

Flide 的解决方案是把每个 Gated DeltaNet 层的计算分成两个阶段。第一阶段，处理所有请求的上下文部分，计算出每个请求上下文结束时的循环状态。第二阶段，处理所有问题分支，每个问题分支从自己所属请求的上下文末尾状态出发，继续往后计算。关键在于，第二阶段里每个问题分支拿到的初始循环状态，是通过 GPU 上的一个索引直接指向第一阶段保存的结果，不需要复制状态数据，只需要一个指针。这个机制论文把它叫做状态分叉，state forking。

有了这两个机制，全注意力层通过掩码隔离分支，循环层通过精确的状态分叉隔离分支，就可以在数学上严格证明：Flide 计算出的每个问题的隐藏状态，与这个问题单独跑一遍前向传播得到的结果，在精确算术下完全相同。论文把这个性质作为命题 3.1 给出，证明方法是对层做归纳，每一层的输入相同则输出相同，逐层推进。

解决了精确性之后，第二个挑战是执行效率。决策请求往往很短，一次前向传播可能只需要几毫秒 GPU 时间。如果每次执行都需要在 CPU 和 GPU 之间大量通信，逐个启动 CUDA 内核，这些调度开销就会成为瓶颈。解决方案是使用 CUDA 图，就是把一系列 GPU 内核调用预先录制成一张图，之后每次执行时只需要触发整张图重放，省去了所有的启动开销。

但 CUDA 图有一个限制：它要求每次重放时，所有内核的形状参数都固定不变。而每轮请求里，请求数量和各问题的长度都在变化，树形结构每次都不一样。如果针对每种树形结构各录一张图，会有组合爆炸的问题。

Flide 的解法是把树形结构完全编码进 GPU 元数据里，图本身只依赖 token 流的总长度。不管这轮请求里有多少个问题、每个问题有多少 token、树的分叉方式如何，只要总 token 数落在同一个长度桶里，就可以复用同一张预录的 CUDA 图，只是在重放前更新一下 GPU 上的元数据缓冲区。这就是论文里说的平图执行，flat-graph execution。初始化时，Flide 录制一组按长度分桶的 CUDA 图，每轮请求选最小够用的那张图，不同的树形结构复用同一张图。如果某轮请求超过了最大图的容量，就沿请求边界拆分成多次重放。

还有一个小优化叫做选择性读出。模型的输出头只需要读每个问题最后一个 token 的隐藏状态来计算概率分布，其他 token 在最后一层的 MLP 计算可以跳过。Flide 在每张图里维护一个固定大小的索引缓冲区，记录需要读出的行号，最后一层只在这些行上运行，对其他 token 什么也不做，这在长上下文多问题的场景里能省掉大量无用计算。

第三个挑战是智能体场景下的增量状态处理。智能体在连续决策时，每一步的上下文和上一步高度重合，只是末尾追加了新的交互内容。如果每一步都从头计算所有的 token，大量重复。Flide 的做法是在上下文里的某个位置保存一个检查点，记录下那个位置的全注意力 KV 缓存，以及每个 Gated DeltaNet 层的循环状态和卷积窗口。下一步请求到来时，如果上下文前半段没有变化，就从检查点恢复，只计算末尾新增的部分和各个问题分支。这个检查点是在正常的前向传播过程中顺带生成的，不额外占用一遍计算。检查点的位置被设计在上下文末尾稍靠前的地方，因为对话里最可能变化的内容通常在末尾。

关于浮点确定性，Flide 还提供了一个可选的批次无关模式。在这个模式下，每个矩阵乘法的归约顺序是固定的，不随批次大小改变，每个问题分支的注意力计算和循环层计算都从自己的分叉点出发，不与其他分支共享归约操作。这样不管服务器上同时处理多少请求，同一个问题的答案始终保持逐位相同。这个模式的代价是吞吐量下降不超过 10%，而 SGLang 的批次无关内核会让吞吐量下降 34%，这是一个显著的改进。

现在来看实验结果。实验在一块 NVIDIA H200 GPU 上进行，测试了四个数据集上的六种工作负载，从每个上下文只有一个问题，到每个上下文平均 48 个问题。模型包括 Qwen3.5 系列从 0.8B 到 27B，以及 Gemma 4 系列从 2B 到 31B，全部使用 bfloat16 精度。对比的基线包括 vLLM、SGLang、SGLang 的多项目评分，以及专门为 Jev 模型设计的 vllm-jev 加 RadixFlow 调度器。

主要结果有三个层次。第一，即使每个上下文只有一个问题，Flide 也比其他引擎更快。在最小的 0.8B 模型上，单请求延迟降低了最多 3.2 倍。这个优势来自于 Flide 更轻量的前端和调度器，以及一次平图重放取代多次内核启动。在高并发下，模型计算本身占主导，这个差距缩小，Flide 与最佳基线持平。

第二，当一个上下文携带多个问题时，优势大幅增长。在所有模型大小和并发级别上，Flide 都是最快的，最多实现了延迟降低 9.5 倍、吞吐量提升 8.5 倍。最大的收益出现在 QuALITY 和 MultiRC 数据集上，因为这两个数据集每个上下文的问题数量最多，而 ForkAttention 只计算一次共享上下文，传统引擎则为每个问题重复计算或恢复。

第三，对于纯全注意力模型 Gemma 4，vLLM 已经通过前缀缓存实现了上下文只算一次，但 Flide 仍然快 1.1 到 2.9 倍。这说明在一次前向传播里统一执行整个请求，比先算共享前缀再为每个问题单独执行，还有额外的效率提升，来自于调度和内核启动开销的节省。

在答案保真度方面，Flide 的 top 答案与 float32 参考结果的一致率，在所有工作负载上都是最高的，或者与 vLLM 非常接近，差距不超过 1.2 个百分点。在批次稳定性方面，从 1 个客户端到 64 个客户端，Flide 的答案变化率最多 0.2%，SGLang 最多 1.7%，vLLM 最多 3.2%。多项目评分的情况最差，分类决策翻转率高达 29%，而 Flide 最多 2.3%。

消融实验在 Qwen3.5-4B 上逐个移除 Flide 的各个组件。去掉状态分叉，每个问题单独跑序列，多问题 QuALITY 文章的延迟增加超过一个数量级。去掉 CUDA 图，单个请求需要逐个启动数千个内核，短输入延迟剧增。去掉平图机制，每个请求需要各自录制图，一轮短 RACE 请求的吞吐量下降超过三分之一。去掉选择性读出，最后一层的无用计算增多，吞吐量进一步下降。每个组件各自消除一类不同的开销，合在一起才给出了 Flide 整体的端到端速度。

在专门的决策模型测试上，Flide 在 Open-Jev-2B 和 Open-Jev-9B 上，对比专门为这两个模型设计的 vllm-jev 加 RadixFlow，短输入上快约三倍，长输入上仍保持 1.7 倍的优势。这说明一个在逻辑请求树上正确抽象的通用引擎，可以超越针对特定模型深度优化的专用系统。

在智能体轨迹场景上，论文重放了真实的 SWE-agent 轨迹数据，对比各引擎在历史不断增长时的每步延迟。Flide 每增加一千 token 的历史，边际延迟仅增加约 1 毫秒，而 vLLM 和 SGLang 则是数量级更高的延迟增长。多项目评分在这个场景下尤其糟糕，因为它每步都要重新计算整个历史。最终 Flide 实现的每秒步数，是最强基线的 4.4 到 7.2 倍。

对于图像场景，Qwen3.5 能处理图像，每张图平均有 11 个是否问题。Flide 把一张图和它所有问题打包成一个请求，对比 vLLM 和 SGLang 把每个问题单独走聊天接口的做法，Flide 的速度是对方的 5 到 7.5 倍，同时答案最接近 float32 参考，准确率三个引擎都很接近，误差在半个百分点以内。

从工程角度还有几点值得关注。启动时间方面，Flide 把所有 Triton 内核预编译成一个独立包，服务器从启动到响应第一个请求只需约 35 秒，而不带预编译包需要 181 秒。对重复出现的状态，Flide 保存了循环状态的检查点，当同一段上下文再次出现时直接从检查点恢复，不需要重算任何块，在 4B 模型上响应时间 18.4 毫秒，vLLM 是 39.1 毫秒，SGLang 是 75 毫秒。

在局限性方面，论文没有明说，但从设计里可以看出几点值得注意的地方。首先，ForkAttention 的 GPU 元数据管理有一定的工程复杂度，对于每轮请求都需要在重放前填充元数据缓冲区，这部分 CPU 侧的准备工作在极短的请求下可能仍然有感知。其次，状态分叉对循环层采用两阶段执行，当请求数量特别多时，两次内核调用的开销相比单次调用会有所增加，不过 CUDA 图已经把这部分摊平了很多。第三，批次无关模式虽然只损失不超过 10% 的吞吐量，但在极高并发下对于追求最大吞吐的场景，这个代价仍然存在。

对于做相关方向研究或工程的人，这篇论文有几个直接可以借鉴的思路。第一，当你的工作负载有天然的树形依赖结构时，把依赖关系编码进 GPU 元数据而不是序列本身，是保持计算语义正确性的关键设计原则。第二，对于混合架构模型，循环状态的精确分叉是处理多分支计算的核心难题，两阶段执行加状态索引是一个可以直接借鉴的解法。第三，把请求结构与 CUDA 图形状解耦，依靠元数据的动态性来弥补图的静态性，是在低延迟场景下同时获得调度灵活性和执行高效性的有效路径。

这篇工作的核心教训是：在设计推理系统时，把工作负载的逻辑结构和物理执行结构清晰地分离，不仅能消除大量不必要的重复计算，还能同时保证数值结果的精确性，而这两件事在此之前人们以为是互相矛盾的。
