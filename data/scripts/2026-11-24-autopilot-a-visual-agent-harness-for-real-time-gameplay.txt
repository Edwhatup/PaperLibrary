真正的问题不是模型够不够聪明，而是当游戏不等你的时候，你的代理系统能不能跟上它的节奏。

这篇论文叫 AutoPILOT，全称是 A Visual Agent Harness for Real-Time Gameplay，来自伊利诺伊大学香槟分校等机构的研究团队。它要解决的核心问题，就是当一个多模态大语言模型去玩实时游戏的时候，为什么它明明很聪明，却打不过一个一直在跑的游戏？

我们先把问题说清楚，再讲解法。

现有的视觉游戏代理，包括目前最好的系统之一 VISTA，基本上都遵循一种叫做"单步代理循环"的设计。什么意思呢？就是模型每次被调用，只能发出至多一个动作，然后等模型再想一次，才能发出下一个动作。这个设计在游戏暂停的情况下没什么问题，就好像一个象棋程序，你不落子它就不走，它可以想多久想多久。但在实时游戏里，这就麻烦了。游戏不会等你，时间一直在走。

想象一个太空射击游戏，你的飞船需要实时躲避子弹。模型看到屏幕，开始思考，思考需要六秒，六秒之后它发出一个"向左移动"的指令，但这时候屏幕上的情况早就变了，子弹可能已经打中你了。而且更关键的是，这六秒里它什么也没干，飞船傻站在那里等死。

这就是这篇论文所说的"时间成本"：在实时游戏里，慢思考会直接导致失败。研究者测了一下，把游戏时钟真正跑起来之后，VISTA 的成功率从 84.1% 直接掉到了 42.9%，掉了四十多个百分点。这个数字很触目惊心。

那你可能会想，能不能让模型看得更好、记得更多，来弥补这个差距？VISTA 本身就是这个思路的产物，它有无损的视觉记忆，可以重新检视过去的帧，工具也很完善。但论文发现，在实时模式下，VISTA 的表现和最简单的基线 Codex harness 几乎一样，分别是 38.3% 和 38.9%。视觉记忆没帮上忙，因为你看的帧已经是六秒前的了，看得再清楚又能怎样？更强的推理也只带来了四到七个百分点的提升。

论文的诊断很明确：瓶颈不在于模型看到了什么，也不在于它记住了什么，而在于它的输出是怎么随时间变成动作的。这第三个维度，才是被忽视的关键。

AutoPILOT 就是针对这个维度提出的解决方案。它的核心思想用一句话说：让一次模型调用，能覆盖游戏里的很多步。

论文给这个设计起了个比喻，非常形象，叫做"飞行员与自动驾驶"。飞行员不需要每时每刻都手动操控，他可以打开自动驾驶，然后在需要决策的时候才接管。AutoPILOT 就是这样：模型是飞行员，它可以把日常操控委托出去，等到关键时刻再被唤醒。

具体怎么做呢？AutoPILOT 给模型提供了三种执行模式。

第一种是原始动作，就是直接发一个键盘或鼠标事件，和之前的系统没有区别，适合需要立即反应的简单操作。

第二种叫做开环宏，英文是 open-loop macro。模型写出一个动作序列，比如"先按向右，再按跳跃，再按攻击"，然后系统按这个序列执行，不用再看屏幕。这就好比你在地图上划好了路线，然后导航自动按路走，不需要每走一步都重新决策。适合那些已经验证过的、比较固定的操作流程，比如游戏里的菜单操作。

第三种是闭环控制器，这是最强的设计，也是 AutoPILOT 增益最大的来源。模型在运行时写一段短小的 Python 函数，这个函数会在沙盒里执行最多 120 秒，它自己读取屏幕、自己决策、自己发动作，大约每 0.4 秒行动一次，完全不需要再调用模型。这就相当于，模型不只是给你出主意，它还帮你写了一个能自主行动的小程序，这个程序比模型本身快多了。

那怎么把控制权交还给模型呢？论文设计了六种"唤醒事件"。第一类来自程序本身：控制器可以主动请求切换控制权，比如它说"我到达目标了，请模型来决定下一步"，或者"我遇到了我不认识的情况，需要帮助"，也可以是程序自然执行结束或者报错。第二类来自系统：比如游戏画面发生了重大变化，说明情况变了，系统自动叫停控制器唤醒模型；或者游戏进入了需要玩家选择的决策界面；或者控制器运行超时。这六种唤醒机制保证了控制委托是安全的，模型不会在不该放手的时候放手，也不会在需要接管的时候还傻等着。

这里有一个细节值得注意，就是重启机制。游戏失败之后会自动重启，这时候如果一个宏在运行，宏会停止并唤醒模型；但如果是控制器在运行，控制器不会被唤醒，它自己能检测到重启标记，然后继续在新的尝试里玩。这意味着模型可以写一个"无论输赢都接着玩"的控制器，大大节省了模型调用次数。

好，说完了方法，再来说评测体系。

这篇论文同时提出了一个新的基准测试，叫 AFK-Bench。AFK 是 Away From Keyboard 的缩写，就是"玩家离开键盘"的意思，这名字起得很有意思，因为测的就是当你什么都不做的时候游戏怎么反应。

AFK-Bench 包含 120 个浏览器游戏，分三种类型，每种 40 个。

第一类叫"敌对实时环境"，就是你不动就会死的那种。比如太空飞船射击游戏，你停着不动，几秒钟内就被摧毁了。这类游戏对时间最敏感。

第二类叫"良性实时环境"，游戏时间在流逝，但你不动不会直接失败，只是浪费时间，比如一个赛车游戏，你停着不开只是落后，不会立刻输。

第三类叫"回合制环境"，游戏只有在你操作之后才推进，比如推箱子谜题，你不动它就等着。

这个分类设计得很聪明，因为它把"慢思考的两种代价"分开了：在敌对实时里，慢思考直接导致失败；在良性实时里，慢思考只是浪费预算；在回合制里，慢思考几乎没有代价。对比三种类型的成绩，你就能精确知道每种代价有多大。

另外，每个游戏都可以在两种时钟协议下运行：实时模式下游戏不会暂停，模型在思考期间游戏照样跑；暂停模式下每次模型调用时游戏会冻结，游戏变成了完全的回合制。两者之间的成绩差，就是实时带来的代价。

每个游戏单次尝试的预算是：最多 100 次模型调用、2000 秒游戏时间、2000 个环境步骤。失败后可以在同一预算内重试。

现在来看实验结果，这里的数字非常说明问题。

用 GPT-6.1 Sol 这个模型，在实时模式下，AutoPILOT 的总体成功率是 68.6%，VISTA 是 38.3%，Codex 基线是 38.9%。AutoPILOT 几乎把成功率翻了个倍。

在敌对实时环境里差距最大：AutoPILOT 62.5%，VISTA 只有 16.7%。

从暂停时钟切换到实时时钟，VISTA 掉了 17.8 个百分点，Codex 掉了 12.8 个百分点，而 AutoPILOT 只掉了 4.5 个百分点。这说明 AutoPILOT 对时钟的敏感程度远低于其他系统。

而且有一个非常有意思的结果：即使把时钟暂停，让所有系统都在同等没有时间压力的条件下比较，AutoPILOT 还是赢了 VISTA，领先 17 个百分点。这说明 AutoPILOT 的优势不只来自于它能在实时下快速行动，还来自于一次模型调用能执行更多步骤，让模型调用预算用得更有价值。

为什么暂停时钟下也能赢？来看一组数字。VISTA 每次模型调用只能走一步，它的 222 次失败中有 208 次是因为 100 次模型调用用完了，平均只走了 78 步。AutoPILOT 则平均用 43 次模型调用走了 681 步，每次调用平均覆盖 16 步。效率差别是量级的。

论文还分析了哪种工具贡献最大。在敌对实时环境里，控制器承担了 98% 的步骤；在良性实时里是 89%；在回合制里，宏占了 36% 的调用和 26% 的步骤。可以看出模型会根据游戏类型自动选择合适的工具，控制器主要用在需要实时反应的场景，宏主要用在可以规划固定路线的场景。

消融实验也给出了很清晰的结论。去掉控制器，把 AutoPILOT 退化成只用宏，敌对实时成功率从 62.5% 降到 50.8%；去掉宏，整体下降幅度不大，主要影响回合制游戏。两种工具都去掉，整体降到 45.8%，敌对实时降到 22.5%。两种工具各自单独都能比 VISTA 强，但组合在一起效果最好、花的 token 最少，只用了 280 万 token，这说明两种模式之间存在一定的互补效应。

关于成本，论文做了一个很直观的对比。AutoPILOT 每次对话的 API 成本是 0.89 美元，VISTA 是 1.50 美元。把单次成功所需的总花费算出来，以 GPT-6.1 Sol 为例，要达到 VISTA 最终成功率所需的总花费，AutoPILOT 只需要 VISTA 的五分之一，37 美元对 180 美元。这是因为 AutoPILOT 每次尝试只用 2 次模型调用，VISTA 要用 8 次，失败后 AutoPILOT 还有预算重试，VISTA 往往调用次数已经耗尽。

关于重试机制的分析也很有意思。在没有任何重试的情况下，AutoPILOT 在敌对实时下赢 11.7%，VISTA 赢 8.3%，差距不大。但随着允许的重试次数增加，AutoPILOT 在 20 次重试后攀升到 54.2% 且还在上升，而 VISTA 在约七次重试后就停在 15.8% 左右上不去了。原因很清楚：VISTA 的每次尝试都是一次调用一步，速度慢、花费多，重试七次就把 100 次调用耗尽了。AutoPILOT 的每次尝试开销很低，能用同样的预算做更多次尝试。

扩展到其他模型的结果怎么样？论文用了五个额外的模型：Claude Opus 5.5、DeepSeek-V4.1-Flash、Qwen4-Max、GLM-5.3-Flash 和 Hy4-flash。AutoPILOT 在所有模型下都胜过 VISTA，领先幅度从 13.3 个百分点到 29.2 个百分点不等。这表明这个设计不是针对某一个特定模型调优的，而是一个普遍有效的机制。

还有一个关于推理力度的结论值得单独说一下。之前的研究发现，让模型用更长时间推理，在实时游戏里反而有害，因为模型想得越久，游戏就跑得越远。但 AutoPILOT 颠覆了这个结论。用 Claude Opus 5.5 时，高推理力度让 AutoPILOT 从 53.3% 升到 69.2%，而 VISTA 只从 30.0% 升到 36.7%。道理很直观：对 AutoPILOT 来说，模型想的时间越长，写出来的控制器越好，而这个控制器之后会独立运行很长时间，前期多花的时间是值得的。推理时间不再是纯粹的负担，而变成了对控制器质量的投资。

论文还做了一个模拟实验，把模型生成速度从每秒 10 个 token 一直提升到每秒 200 个 token，来看生成速度对两个系统的影响。VISTA 在 200 个 token 每秒下能到 38.8%，但暂停时钟下是 57.5%，说明即使模型变得很快，单步循环的天花板仍然在那里。AutoPILOT 在 10 个 token 每秒的情况下就已经很强，因为一旦控制器跑起来，它就以游戏速度行动，不再受生成速度的约束。

最后在 GameWorld 这个独立的基准上也验证了同样的结论。这个数据集有 170 个任务覆盖 34 个游戏，和 AFK-Bench 完全没有重叠。暂停时钟下 AutoPILOT 和 VISTA 相差无几，84.1% 对 82.9%。但实时模式下，VISTA 掉了 41.2 个百分点，AutoPILOT 只掉了 2.9 个百分点。这种对时钟的鲁棒性在全新的游戏集上完整地复现出来了。

当然，这篇工作也有局限性需要注意。首先，它只处理纯视觉输入，不读取游戏的底层状态，这既是它的设计原则——通用性强，不依赖游戏接口——也意味着感知能力有上限，模型写的控制器有时可能在视觉判断上出错。其次，控制器是运行时生成的 Python 代码，质量依赖模型的代码能力，对代码能力弱的模型可能效果打折。第三，沙盒运行有资源限制，复杂的视觉处理可能放不进去。第四，论文的游戏都是浏览器轻量游戏，对 3A 大作或者更复杂的实时场景还有待验证。

那对于我们自己的研究和实践，这篇论文能借鉴什么？

如果你在做任何涉及实时或高频决策的代理系统，不管是游戏、机器人、GUI 操作还是其他，这篇论文最核心的启示是：把"模型输出怎么随时间变成动作"当作一个独立的设计维度，而不是默认沿用单步循环。让一次调用覆盖多步，把日常执行委托出去，只在关键时刻唤醒慢思考，这个结构性的改变比提升感知能力或记忆能力的边际收益大得多。唤醒机制的设计也值得借鉴，六种条件的组合确保了委托的安全边界，这个思路可以迁移到任何需要"主控制器与子执行器"协作的场景里。另外，实验中发现推理时间可以从代价变成投资这一点，也对代理系统的成本分析有启发：与其追求更快的模型响应，不如让慢思考产生更持久的行动效果。

代理系统的设计，不能只盯着感知和记忆，时间上的行动结构同样是核心，而且往往是更被忽视的那个核心。
