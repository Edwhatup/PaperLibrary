现有的语言智能体评测基准，几乎全都把人类用户这个环节给省掉了。典型的设置是：给智能体一个完整的任务描述，让它自己去操作网页、执行代码、调用API，然后看结果。这种设置的问题在于，它和真实世界的客服、助手场景差距太大。真实场景里，用户不会一次性把所有信息说清楚，对话是渐进式的，智能体需要一边问一边推断；同时，智能体还必须遵守一套复杂的领域规则，比如航空公司的行李政策、退款政策、不同会员等级的差异化处理。这两件事——和人交互、遵守规则——恰恰是部署真实智能体最核心的能力，但现有基准对它们的测试几乎是空白的。

这就是这篇论文要解决的问题。来自Sierra的研究团队提出了一个叫做tau-bench的基准，全称是Tool-Agent-User Interaction Benchmark，专门用来测试语言智能体在和模拟用户对话的同时、调用领域API工具、遵守领域特定规则这三件事上的综合能力。这个基准的出现，填补了现有评测体系中"人在回路"这个关键维度的空白。

我们先来理解这个基准的整体设计思路。tau-bench把每个任务建模为一个部分可观测的马尔可夫决策过程，这个术语听起来复杂，但核心意思很简单：智能体看不到完整的世界状态，它只能通过行动来逐步获取信息。智能体面对两个交互对象：一是数据库，通过API工具来读写；二是模拟用户，通过自然语言来沟通。数据库的状态是隐藏的，智能体必须调用特定的API函数才能看到相关信息。用户的状态则由一个大语言模型来扮演，这个模拟用户有自己的身份、意图和偏好，但不知道智能体和API之间发生了什么。

这个设计非常贴近现实。想象一个航空公司的客服系统：用户打电话来说"我想改一下我的机票"，客服代理需要先核实用户身份，然后查询预订信息，检查相关政策，再和用户确认具体需求，最后才能执行操作。整个过程是多轮的，是不确定的，每一步都可能出现新的信息或者约束。

论文目前构建了两个领域。第一个是tau-retail，零售客服场景，智能体需要帮用户取消或修改待处理订单、退货或换货已交付订单、修改地址等。数据库包含500个用户、50种产品、1000个订单。API工具有15个，其中7个会修改数据库状态，另外8个只是读取。第二个是tau-airline，航空客服场景，智能体需要帮用户订票、改签、取消、退款。数据库规模更大：500个用户、300个航班、2000个预订记录。这个领域的策略文档也更复杂，涉及不同会员等级的免费行李额度差异、不同舱位的改签限制、组合支付方式的规则等等。

这两个领域的构建分三个阶段完成。第一阶段是人工设计数据库模式、API接口和领域政策。研究人员的原则是"尽量简单，但不能失真"——数据库模式要有内在一致性，API要像真实系统那样有合理的报错和约束，策略文档要覆盖真实业务中会出现的各种规则。第二阶段是用大模型自动生成数据库内容。研究人员先写一个示例条目，然后让GPT-4生成批量采样代码，再人工修正小错误。第三阶段是最费工夫的：人工设计任务场景并验证。每个任务场景要保证用户指令在领域政策下有且只有一个正确的数据库操作结果，不能有歧义。做法是先写一个初始指令，跑一次试验，检查轨迹，修改指令，循环迭代，直到确认没有歧义为止。

这里有一个关键的设计选择值得单独讲：为什么要保证唯一结果？因为评测方式是直接比较任务结束时的数据库状态和预标注的"正确"数据库状态。如果一个任务有多种合理的处理方式，那数据库状态就会不同，评测就失去了客观性。通过保证唯一结果，论文用规则性的数据库比对替代了主观的人工评判，这样评测速度快、结果可复现、不依赖人工。当然，这是一种权衡：规则评测可能遗漏一些语义上正确但数据库操作有细微差别的情况，但论文的实验表明，这个评测方式已经足够严格，现有最强的模型都远未达到满分。

tau-bench的奖励函数设计也值得关注。整体奖励等于两个分量的乘积：一是数据库操作是否完全正确，二是智能体的回复中是否包含用户询问所需的必要信息。比如某个任务里用户问了退款金额，智能体必须在回复中包含具体的数字，否则即使数据库操作对了，奖励也是零。两个分量都是零或一，最终奖励只有完全成功才是一，部分正确得零分。这种严格的评测标准在实践中其实是合理的——客服系统要么解决了问题，要么没解决，中间状态对用户来说意义不大。

现在讲这篇论文最重要的技术贡献之一：pass-k这个新指标。在代码生成领域，社区有一个叫pass@k的指标，意思是"k次独立尝试中，至少有一次成功的概率"，这反映了模型在有足够多尝试时能否找到正确答案。但对于客服智能体这类真实世界应用，这个指标是不够的。客服系统不是在帮你找答案——它是在直接服务用户，每一次对话都必须成功，不能靠"多试几次取最好的"来兜底。

所以论文提出了pass-k，上标是一个小帽子符号，意思恰好相反：k次独立尝试中，每一次都成功的概率，再对所有任务取平均。这个指标衡量的是智能体的一致性和可靠性。如果一个模型的pass-1是60%，意味着平均60%的任务能成功，听起来还不错。但pass-k会随着k增大而快速下降——如果每次成功的概率独立地是60%，那8次全部成功的概率就是0.6的8次方，大约1.7%。当然实际情况不完全是独立的，因为同一任务的用户模拟每次都有随机性，但底层数据库和规则是固定的，所以pass-k捕捉的是智能体在面对同一任务的不同对话变体时，能否稳定地做出正确决策。

实验结果非常能说明问题。我们来看具体数字。在function calling这种方法下，也就是让模型原生支持的工具调用模式，GPT-4o是表现最好的模型，在tau-retail上的pass-1是61.2%，在tau-airline上只有35.2%。GPT-4-turbo是57.7%和32.4%，GPT-4-32k是56.5%和33%。注意，tau-airline显著比tau-retail难，主要是因为策略更复杂、规则更多。

往下看，Claude-3-Opus在tau-retail是44.2%，tau-airline是34.7%，整体表现比GPT-4o差但差距不算太大。Gemini-1.5-Pro在tau-retail只有21.7%，tau-airline只有14%，表现相当糟糕。开源权重模型方面，Llama-3-70B只有14.8%和14.4%，mixtral-8x22b是17.7%和31.6%，和顶级闭源模型有非常显著的差距。

这些pass-1的数字已经足够令人警醒——最强的模型在更难的领域只解决了三分之一的任务。但pass-k的结果更加触目惊心。GPT-4o在tau-retail的pass-1是61%多，但pass-8只有不到25%。也就是说，即使是目前最强的模型，如果同一个任务运行8次，全部成功的概率不到四分之一。GPT-4-turbo和Claude-3-Opus的pass-8更低。GPT-3.5-turbo的pass-8在tau-retail接近零。

这个结果揭示了一个深层问题：当前的语言智能体在处理同语义、不同表达的对话变体时，行为高度不稳定。用户今天用A的方式说，可能成功；明天换了个表达方式说同一件事，就可能失败。对于每天处理数百万次对话的真实系统来说，这种不稳定性是不可接受的。

在方法比较方面，论文测试了三种agent构建方式：function calling、ReAct和纯Act。Function calling是让模型用原生支持的结构化工具调用格式；ReAct是让模型先输出思考过程，再输出JSON格式的行动；纯Act是只输出行动，没有显式的推理步骤。结果表明，在支持原生function calling的模型上，function calling方式表现最好。ReAct比纯Act好，说明显式的推理步骤有帮助，可以帮助模型在不熟悉的格式和观察之间建立桥梁。有趣的是，研究人员尝试给function calling模型加一个"think"函数，让它在调用工具前先做显式推理，但这并没有带来提升，可能是因为这些模型并没有被专门训练成以这种方式推理。

论文对失败案例做了很细致的分类分析，聚焦在GPT-4o function calling agent在tau-retail上的表现。在115个任务中，有40个失败，排除4个因为任务标注本身有歧义被修正的情况，还剩36个真正的智能体失败案例。论文把这36个案例分成四类。

第一类是参数错误，占19.4%。智能体调用了正确类型的工具，但填错了参数。论文举的例子是用户想把一盏台灯换成亮度更低、且使用AC适配器而不是电池或USB供电的版本，智能体无法在复杂的商品库存中推理出满足这两个条件的唯一选项。弱一些的模型在这方面的问题更严重，比如GPT-3.5-turbo平均每个任务会产生2.08次幻觉参数调用，也就是用一个不存在的用户ID或商品ID来调用函数；而纯Act模式下GPT-3.5-turbo这个数字高达6.34次，相比之下GPT-4o只有0.46次。

第二类是错误信息，占25%。智能体遗漏了用户要求的信息，或者计算了错误的金额，或者提供了错误信息导致用户做出了错误的后续决策。比如用户问退款多少钱，智能体给了一个错误的数字，用户基于这个错误数字决定不退货了，实际上如果知道正确金额她是会退的。这类失败加上参数错误一共占了大约55%的失败案例，核心问题是智能体在复杂数据库上的数值推理和常识推理能力不足。

第三类是决策错误，占25%。这类失败不是参数填错了，而是做出了错误类型的操作，根本原因是没有理解或遵守领域规则。论文举的例子很典型：用户说想换"一两件东西"，根据领域政策，换货工具只能调用一次，必须把所有要换的东西一起提交。但GPT-4o选择先换一件，再换另一件，结果第二次调用失败，因为该工具已经用过了。这说明智能体虽然看到了策略文档，但并没有真正理解并执行其中的约束。

论文还做了一个消融实验来量化规则遵守的重要性：把领域策略文档从智能体的系统提示中去掉，看成绩下降多少。结果很有意思：在tau-retail里，去掉策略后GPT-4o只下降了4.4%，GPT-3.5-turbo只下降了5.5%，说明这两个模型在零售场景里的成功大多靠的是常识，而不是真正在利用策略文档。但在规则更复杂、更非常识性的tau-airline里，去掉策略后GPT-4o大幅下降了22.4%，说明它确实在一定程度上依赖策略文档；而GPT-3.5-turbo只下降了1.2%，说明它根本没有能力处理航空公司那么复杂的规则，有没有策略文档对它来说区别不大，因为它本来就学不会。

第四类失败是部分完成复合请求，占33.3%，是四类里比例最高的。当一个任务包含多个用户请求时，智能体经常只处理其中一部分。论文有一个例子：用户想修正所有订单中的错误地址，但智能体查了一个订单之后就停下来了，没有系统地把所有订单都检查一遍。随着任务需要的数据库写操作数量增加，成功率也在快速下降，从需要1次写操作的任务到需要4次写操作的任务，成功率下降非常明显。这反映了智能体在长上下文记忆和系统性执行上的薄弱。

关于用户模拟的可靠性，论文使用GPT-4-0613来扮演用户，温度设为1.0以产生自然的随机性。这个设计有一个重要的优点：同一个任务每次运行，用户的具体措辞不同、追问方式不同、信息透露的节奏不同，这些变化是自然且合理的，正好可以用来测试智能体的鲁棒性。论文也坦诚地指出了用户模拟的局限：模拟用户有时会在不完全理解某个约束的情况下做出授权决定，比如用户批准了智能体推荐的台灯，但没有仔细核对它的规格是不是真的符合自己的要求。这反映了真实用户的局限性，论文的立场是，正是因为真实用户可能不理解复杂的领域规则，智能体才更需要主动、全面地确保操作正确性，不能依赖用户来纠错。

在成本方面，论文做了一个估算：在tau-retail上，用GPT-4o当智能体、GPT-4模拟用户，每个任务每次试验的费用是：智能体约0.38美元，用户模拟约0.23美元，合计约0.61美元。运行115个任务各一次大约需要70美元，而成本的大头——将近96%——来自智能体端的输入token，主要是长系统提示（包含领域策略和API定义）。这个数字对于想在自己领域复现实验的研究者来说，是一个重要的参考。

对于局限性，论文也做了坦诚的讨论。目前只有零售和航空两个领域，都是相对容易构造合成数据的场景。更高专业度的领域比如医疗、税务、法律，规则更复杂、数据更难合成，是未来可以扩展的方向。任务标注过程人工负担很重，而且存在一定的隐性偏差，因为任务的标注和调试都用的是GPT-4-turbo这个模型，对其他模型可能不完全公平。规则评测虽然客观，但可能遗漏一些语义上正确但数据库操作有细微差异的情况，未来可以用语言模型辅助检查某些规则是否被遵守，作为补充。

从这篇论文，研究语言智能体的从业者可以得到几个非常具体的启示。第一，单看平均成功率是不够的，pass-k这种一致性指标更能反映实际可用性，任何想把智能体部署到真实系统的人都应该把稳定性放在和准确率同等重要的位置来衡量。第二，函数调用能力的基础测评，比如Berkeley Function Calling Leaderboard那类只测单轮调用的基准，和真实的多轮用户交互场景有本质差距，需要在评测体系中引入对话层面的测试。第三，策略文档的遵守问题是一个严重被低估的挑战，尤其是当规则复杂且反常识时，模型几乎没有能力可靠地提取和执行，这可能需要专门的训练或架构设计，比如领域特定的微调或者代码级的约束检查。第四，复合请求的系统性处理是当前模型的一个明显短板，如果要提升这方面的能力，需要更好的任务追踪机制和长上下文记忆能力。

当前最好的语言模型在真实客服场景下，连一半任务都无法稳定完成，这不是一个可以用"模型再强一点就好了"来轻松打发的问题，它指向的是整个智能体架构在一致性、规则遵守和多轮交互上的系统性短板，而这正是下一代真正可部署的智能体系统需要着力突破的核心方向。
