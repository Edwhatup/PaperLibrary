SWE-Pruner Pro: The Coder LLM Already Knows What to Prune

No notes on this paper yet — it's on the reading list.

Audio digest (电台)

Abstract

Pruning long context for coding agents has been a vital technology for efficient context management. While existing context pruning methods such as SWE-Pruner realize this by attaching a separate code classifier, we find the agent itself encodes internal representations indicating the relevance of code context when reading tool output. Based on this finding, we propose SWE-Pruner Pro, which prunes tool outputs directly inside the agent. Concretely, a small head turns the agent's own internal representations into a keep-or-prune label for each line, with a length-aware embedding keyed to each tool output's line count. Across two open-weight backbones and four multi-turn benchmarks, SWE-Pruner Pro saves up to 39% of prompt and completion tokens while preserving task quality, with bounded inference overhead. Notably, on MiMo-V2-Flash SWE-Pruner Pro additionally raises the SWE-Bench Verified resolve rate by +3.8% and the long-context Oolong accuracy by +2.2 points.

Chinese digest · 导读全文

编程智能体在处理真实代码库任务时，会反复调用工具去读取文件、搜索代码、执行脚本。每一次工具调用都会返回一大段文本，这些文本被原样塞进上下文窗口，随着对话轮次增加不断累积。问题就在这里：这些工具输出里充满了冗余信息，绝大多数内容要么已经看过，要么根本不会再被用到，但它们仍然占据着宝贵的上下文空间，让模型每次生成都要处理更长的提示词，既费钱又容易出现长上下文退化的问题——就是那种越到后面模型越"忘事"、注意力越散的现象。

所以裁剪上下文，或者说上下文剪枝，成了一个重要的工程方向。这篇论文要解决的核心问题是：怎么才能又准又省地从工具输出里删掉没用的行，同时不破坏智能体的任务表现？

现有的方法大致分两类。第一类是通用的提示词压缩方法，比如LLMLingua系列或者Selective Context，它们用困惑度或者自信息这类静态指标给每个词打分，然后把低分的词删掉。这类方法的问题是，它们完全不知道智能体当前在干什么，也不知道任务目标是什么，用一套固定标准打分，当然无法适应智能体在不同轮次不同焦点下的需求。第二类是任务感知的剪枝方法，代表就是这篇论文的直接前身SWE-Pruner。SWE-Pruner的做法是让智能体每一轮生成一段"目标提示"，描述当前任务的意图，然后用一个单独的评分模型，结合这个目标提示，来判断工具输出的每一行是保留还是删除。这个方法比第一类聪明很多，因为它知道任务背景。但它有一个显著的成本：每一轮都要调用一个额外的模型，还要让智能体额外生成那段目标提示，增加了系统复杂度和推理开销。

这篇论文的作者团队在这里问了一个非常好的问题：智能体自己在读工具输出的时候，它的骨干模型内部不是已经在做前向传播、处理这些文本了吗？它内部形成的隐状态表示，难道没有编码"哪些行重要、哪些行可以忽略"的信息吗？如果这个信息已经在模型里了，为什么还要从外部花额外代价去重建它？

为了验证这个直觉，他们做了一个探测实验。他们从公开的SWE-Bench风格数据集里收集了大量多轮工具响应，用Claude Sonnet 4.6给每一行打上"保留"或"删除"的标签。然后冻结Qwen3-Coder-Next这个编程大模型的所有参数，对每一行的最后一层隐状态做均值池化，得到每行的向量表示，再用一个简单的逻辑回归分类器，看这两类行在表示空间里是否可分。

结果很清楚：两类行的均值在隐状态空间里确实不同，沿着线性判别分析的主方向可以看到明显的分布偏移。在留出的测试轨迹上，这个简单的线性探针达到了不错的AUC分数，远高于多数类基线。也就是说，"保留还是删除"这个判断，已经编码在骨干模型的内部表示里了。这就是整篇论文方法的动机所在：与其在外面费力重建这个信号，不如直接从模型内部把它读出来。

但线性探针也暴露了局限：在中等分数的灰色地带，两类样本有相当多的重叠，光靠线性分类器无法完全区分。另外，工具输出的长度差异很大，短的可能只有五行，长的可能有几百行。对五行的输出错删一行和对三百行的输出错删一行，代价完全不对等。这两个问题，一个需要非线性的分类头来解决，另一个需要长度感知机制来解决。这就引出了SWE-Pruner Pro的具体设计。

整个系统的运作方式是这样的。智能体每轮调用工具、得到工具响应之后，在智能体生成下一步动作之前，骨干模型会先对工具响应做一次前向传播，也就是prefill，把这段文本的KV缓存计算好，同时产生每个词的最后一层隐状态。SWE-Pruner Pro就挂载在这个prefill过程上，把这些已经产生的隐状态拿来用。注意，这一步骨干模型无论如何都要做，不是为了剪枝新增的开销，所以可以认为是"搭便车"。

然后，一个轻量级的分类头对每个词的隐状态做预测，输出这个词是"保留"还是"删除"的概率。预测完之后，按行做多数投票：一行里超过一半的词预测为保留，这行就保留，否则就删除。为什么按行而不是按词？因为代码的语义单元是行，一行代码要么整体有意义要么整体可以去掉，按词删会破坏语法结构。这与SWE-Pruner的设计一脉相承，都在行级别操作。

分类头的结构是这样的：先做LayerNorm，然后两层线性变换加GELU激活加Dropout，最后一个线性层输出单个逻辑值。隐藏维度和骨干模型的隐藏维度一致，所以换骨干时头的大小也会跟着变，但骨干参数完全冻结，不需要任何微调。

现在说说那个长度感知嵌入，这是一个设计上很精妙的地方。系统把工具响应的总行数分成若干个区间，比如零到两行、三到五行、六到十行，一直到超过两百行，每个区间学习一个嵌入向量。当分类头处理某个工具响应时，先根据这个响应的总行数查到对应的区间嵌入，然后把这个嵌入加到所有词的隐状态上，再送入分类头。这个嵌入在训练开始时被初始化为零，所以在训练初期它不产生任何影响，头先学会基础的保留删除判断，随着训练进行再逐渐学习如何根据长度调整策略。加入这个机制的效果是：面对一个只有五行的工具输出，头会知道要格外保守，轻易不删；面对三百行的输出，头可以更激进地删掉重复和无关的行，因为偶尔删错几行的代价相对来说小得多。

训练数据来自五个公开的HuggingFace数据集，涵盖了SWE风格的代码修复轨迹和各种命令行任务轨迹。他们用Claude Sonnet 4.6对大约两万两千个样本的每一行做了标注，标注时让模型看到完整的历史上下文、当前工具调用、工具响应和下一轮的动作，来判断哪些行是智能体真正需要的。整个语料库的平均保留率大概在五成左右，但有些样本只保留百分之三的行，有些保留百分之九十，分布非常不均匀。

这个不均匀分布引出了损失函数的设计问题。普通的交叉熵损失在全局层面上把所有词一视同仁，面对一个只有三行保留、九十七行删除的样本，它会被那九十七行的梯度淹没，三行保留行对训练几乎没有贡献，但这三行恰恰是最关键的信息。批次级别的Focal Loss可以稍微缓解这个问题，但它是在整个批次层面看类别频率，仍然无法感知单个样本内部的极端不平衡。

作者提出的解决方案是"per-sample balanced focal loss"，也就是逐样本平衡的焦点损失。做法是：在每个样本内部，分别对保留行和删除行各算一次Focal Loss，然后两个损失各取一半加权平均，再在样本间做平均。这样，不管一个样本里保留行有多少、删除行有多少，两个类别在这个样本对训练的贡献里各占百分之五十。一个极端稀疏的保留样本，它那几行保留行会得到和它删除行同等的梯度权重，这正好符合直觉：越稀少的保留行，越代表着这个场景里真正不可或缺的内容，应该让模型更重视它。

消融实验专门对比了这个损失函数和四个替代方案：普通二值交叉熵BCE、批次级别Focal、Dice Loss和Tversky Loss。结果是per-sample balanced focal在法官评分和F1两个指标上都最好，比BCE高出了明显的差距。有一个有趣的发现：Dice和Tversky这两种损失在F1上和最优方案很接近，但法官评分却大幅下滑。为什么会这样？因为F1衡量的是你选出的行集合和标注集合的重叠程度，一个分类头如果只保留它最有把握的几行，精准度很高，F1也不会太差。但法官问的是：智能体拿到这个被裁剪过的工具输出，能不能完成下一步动作？你保留了函数签名但删掉了函数体，F1可能还不错，但智能体根本看不懂。所以论文同时报告F1和法官分数是有必要的，两个指标衡量的是不同维度的质量。

长度感知嵌入的消融实验表明：加上这个嵌入之后，法官评分从基础版本提升了接近一个点，而F1几乎没有变化。这说明长度嵌入不改变整体的行级别判断准确率，但它重新分配了错误的位置——它让模型把更多的错误集中到长响应上，在那里错删几行代价低；而在短响应上变得更谨慎。这正是设计意图。

现在说说实验结果。论文在四个基准上评测了SWE-Pruner Pro，分别是SWE-Bench Verified，这是一个包含五百个真实GitHub问题的代码修复任务；SWE-QA和SWE-QA-Pro，这两个是多轮问答任务；以及Oolong，这是一个长上下文聚合任务，论文把它改造成了多轮工具调用的形式。两个骨干模型分别是MiMo-V2-Flash，一个三百零九亿参数的混合专家模型；和Qwen3-Coder-Next，一个八十亿参数的紧凑型编程专用模型。

在SWE-QA家族和Oolong上，SWE-Pruner Pro是七种方法里唯一在每个测试格子上都减少了端到端Token用量的方法，最高节省达到了百分之三十九，同时任务质量保持在未剪枝基线的附近。对比鲜明的是：其他六种方法里有四种在至少一个测试格子上反而增加了Token消耗，LLMLingua2在Oolong上甚至让Token用量暴涨了百分之一百七十多。为什么会增加？因为这些方法有额外的开销——要调用额外的评分模型、要生成目标提示、要做检索操作——这些开销本身也消耗Token，当压缩增益抵不过额外开销的时候，净效果就变成了负的。

质量方面，在Qwen3-Coder-Next上，RAG方法确实保住了任务质量，但它的Token节省几乎可以忽略不计，而且它引入的检索开销本身也不小。其他压缩效果明显的方法，比如SWE-Pruner和Self-Prune，都在某些设置上牺牲了质量。SWE-Pruner Pro是唯一同时做到大幅减少Token又保持质量的方法。

在SWE-Bench Verified这个更重的代码修复任务上，结果有一些有趣的不对称性。MiMo-V2-Flash作为骨干时，所有剪枝方法都提升了解决率，而SWE-Pruner Pro在只用约一半Token开销的情况下，达到了所有方法里最高的解决率提升。这个结果有点出乎意料——剪枝不仅没有损害效果，反而提升了效果。一个可能的解释是：对于这个骨干模型，工具输出里的冗余信息确实干扰了它的推理，删掉这些内容让模型更聚焦。Qwen3-Coder-Next作为骨干时，所有剪枝方法都损失了一些解决率，但SWE-Pruner Pro的损失最小——只丢了六个解决案例，同时实现了最大的输入Token减少，比其他方法在质量和效率的权衡上都更优。

关于推理延迟，论文在一个十六轨迹的MiMo-V2-Flash回放实验里测量了剪枝头的实际开销。整体附加时间只占智能体总生成时间的百分之十五，单轨迹的比例在百分之七到百分之二十五之间。这个开销有界且可控，原因在于头复用了骨干本来就要做的prefill，没有额外的模型调用。而且这个百分之十五的开销只发生在每轮剪枝时，节省的Token却在随后每一轮的生成里都持续发挥效果，所以整个轨迹下来净节省是正的。论文还提到了一个进一步的优化：把分类头直接集成进推理引擎内部，这样连跨进程传输隐状态的网络开销也省掉了，聚合延迟可以从百分之十五降到更低。

说到这个方法的局限性，有两点需要诚实地指出。第一，SWE-Pruner Pro需要访问骨干模型的内部隐状态，所以目前只能用在开源模型上，对GPT-4o或Claude这类只提供API的闭源模型不适用。作者说这个框架本身可以推广到任何暴露隐状态的模型，但当前评测范围确实只涵盖开源模型。第二，训练数据和主要基准都是Python为主，论文用Oolong这个自然语言长上下文任务做了跨领域检验——在这个非代码任务上SWE-Pruner Pro仍然保持了Token节省和质量，说明方法有一定的通用性，但更广泛的编程语言覆盖留给了未来工作。

对于从事智能体系统或大模型推理效率方向的工作来说，这篇论文有几个值得借鉴的具体点。第一，探针实验的设计思路很有价值：在提出一个方法之前，先做一个轻量级的线性探测实验，证明目标信号确实存在于模型表示空间里，这是一种严谨且有说服力的动机建立方式，可以直接用在类似的"模型内部有没有编码某种信息"的研究问题上。第二，per-sample balanced focal loss这个损失函数设计值得记住，凡是训练数据里存在样本级别不均衡（而不只是全局不均衡）的场景，这个设计都可能比批次级别的处理更有效。第三，长度感知嵌入的零初始化技巧是个简洁的工程惯例：让辅助的条件信号在训练开始时不干扰主要信号的学习，随着训练进行再逐渐发挥作用，这种设计降低了超参数的敏感性。

最根本的启发是这篇论文揭示的一个更广泛的原则：大语言模型在被动处理观测信息的时候，已经形成了关于信息重要性的内部判断，而以往很多方法花额外代价从外部重建的，恰恰是模型内部早就有的东西——直接从内部读出来，往往既更准确又更高效。
