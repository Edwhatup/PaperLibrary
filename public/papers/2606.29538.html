RESOURCE2SKILL: Distilling Executable Agent Skills from Human-Created Multimodal Resources

No notes on this paper yet — it's on the reading list.

Audio digest (电台)

Abstract

Skills are a useful abstraction for software agents, turning human and agent experience into reusable procedural knowledge. Yet existing skill libraries are mostly hand-written, text-centric, or derived from agent traces, leaving tutorial videos and other multimodal human resources largely underused. We present RESOURCE2SKILL, a framework that distills multimodal resources, including tutorial videos, repositories, articles, and reference artifacts, into executable skills for software agents. RESOURCE2SKILL organizes these skills as a hierarchical multimodal Skill Wiki, where each entry combines structured text, code, visual examples, metadata, and provenance. This design preserves complementary signals from different resources: videos capture temporal operations and visual effects, code captures executable tool patterns, and articles or artifacts provide conceptual and stylistic grounding. At inference time, agents retrieve and compose relevant skills from the wiki; when coverage is insufficient, the same construction operator can acquire new skills online. Across seven practical authoring domains, RESOURCE2SKILL improves average overall score by +11.9 percentage points over no-skill agents and outperforms strong harness baselines in 26 of 28 main-aggregate model-domain cells. Ablations confirm the value of multimodal skill format, hierarchical organization, source diversity, selection strategy, and online acquisition.

Chinese digest · 导读全文

你有没有想过，给AI智能体一个"技能库"，让它在操作软件时不用每次都从零开始推理？这篇论文要解决的，正是这个问题——而且它瞄准了一个几乎被所有前人忽视的知识来源：人类创作的教程视频和其他多模态资源。

让我先把问题说清楚。当我们让一个大语言模型智能体去完成复杂的软件操作任务——比如在Blender里搭建一个三维场景、在PowerPoint里设计一套精美幻灯片、用Unreal Engine 5构建一个实时渲染关卡、或者在REAPER里做音频混音——成功与否往往不取决于模型知不知道某个孤立的事实，而取决于它是否掌握了可复用的操作流程知识。怎么分解目标、调哪个API、执行到哪一步该检查什么中间状态、出错了怎么恢复——这些东西统称为"技能"，也就是可复用的程序性知识。

问题在于，现有的技能库都是怎么建起来的？要么是人类专家手写的，要么是从智能体自己的交互历史里积累的，要么是从纯文本和代码库里挖掘出来的。这三种来源都有根本性的局限。对于很多商业创意软件来说，人类学习这些工具最自然的方式不是读文档，而是看教程视频。一个五分钟的屏幕录制教程，能展示出操作的时序顺序、每一步编辑后的视觉效果、还有那些很难用文字表达的心照不宣的设计选择。这些信息，对于软件操作来说至关重要，但它们在现有的技能库里几乎是空白。

那为什么以前没人做？因为直接用视频作为智能体的上下文，代价极其高昂。一个教程视频里充斥着无关紧要的开场设置、重复的讲解、以及只在少数关键帧才有意义的视觉细节。你不能把原始视频塞进模型的记忆里。但如果你把视频压缩成纯文本摘要，你又恰恰丢掉了视频最有价值的那部分——动态操作、前后对比的视觉变化、动画质量、空间布局、时序节奏、工具交互顺序。这是一个两难困境。

这篇论文提出的方法叫Resource2Skill，它的核心思路是：不要直接用原始视频，而是把视频以及其他多模态资源——包括代码仓库、技术文章、参考工件——提炼成结构化的、可执行的技能条目，组织成一个有层级的多模态"技能维基"，让智能体在推理时检索和使用。

我们来细看这个设计。每个技能条目是一个包含多个互补视图的数据结构。文本视图说明这个技能叫什么名字、工作机制是什么、适用场景、所需输入、预期效果。视觉视图包含缩略图、截图、渲染预览或图表。代码视图包含可执行或可适配的程序片段。再加上元数据和来源溯源信息。这个设计是有意为之的——文本解释了适用性和机制，代码提供了工具层面的执行模板，视觉材料保留了布局、风格、运动等纯文本无法充分刻画的感知信息。

整个框架分四个阶段：构建阶段、维基组织阶段、选择阶段、执行阶段。

先说构建阶段。给定一个目标领域，系统从四类资源中提取技能：教程视频、源代码仓库、技术文章、参考工件。一个多模态提炼算子对每个资源进行处理——视频的话就是关键帧采样，代码仓库的话就是基于抽象语法树的代码区域提取，文章的话就是段落分割，工件的话就是图像预处理。然后用一个具有视觉理解能力的语言模型把这些证据蒸馏成标准的技能条目JSON结构。提炼完成后，会经过一个五重验证谓词：完整性检查确保所有必要字段都填写了；溯源检查确保来源可追溯；去重检查基于SHA1哈希避免重复；模态一致性检查确保声明的模态文件真实存在；最后还有结构可执行性检查，对于有代码字段的条目，会在沙盒里实际跑一下，确认代码结构上可运行并能产出非空工件。不能通过可执行性检查的条目不会被丢弃，而是保留为"仅参考"条目，智能体可以从中读取文本和视觉证据来自己写代码。

再说维基的层级组织。这是与之前工作的一个关键区别。以前的技能库基本上是平铺的，检索靠向量相似度或BM25词法匹配。Resource2Skill把技能组织成一棵领域特定的分类树。举几个例子：PPT领域按布局、排版、调色板、图表、图标、运动等类别组织；Blender领域按几何体、材质、光照、构图等类别组织；CAD领域按图元、约束、标注、填充、图层等类别组织。这棵树不只是个目录，它在检索时直接发挥作用。

选择阶段用的是一个叫MetaBrowse的两阶段策略。第一阶段是词法评分，把技能的名称、标签、适用性文本、以及——注意这里——技能在分类树里的路径一起纳入评分，这样一来分类树就直接偏向于把分布在拓扑上相关子树里的技能排到前面，而不是把整个库当成平铺列表处理。这一步缩小候选集范围。第二阶段是让语言模型从候选集里读取结构化证据，选出一个子集来组合使用。注意选出来的是一个子集而不是一个排名——语言模型可以选零个技能，如果没有一个候选是合适的。

执行阶段的设计也值得一说。智能体和领域适配器共享一套统一的MCP工具接口——MCP是一种标准化的模型与工具交互协议。维基侧暴露的是发现动作：列出类别、列出带元数据卡片的技能、读取特定模态的内容、以及一个包装了BM25短名单的搜索动作。领域侧暴露一个apply动作，当某个能力不支持时会返回结构化的"不适用"响应。每次运行都遵循相同的控制循环：规划任务、MetaBrowse选技能、apply执行、渲染工件。当选出的技能里有可执行代码时，代码直接在MCP服务器上运行，中间不需要语言模型再做翻译——这一点保证了执行的确定性。

还有一个重要机制是在线获取。当离线库里没有足够合适的候选技能时，同一个构建算子可以在线调用：对同样的资源类型发出针对性查询，把返回的资源实时提炼成临时候选，通过验证后作为一个独立的在线池暴露给当前任务。关键是离线库和在线获取的池子是严格分开的，在线获取是受控的能力补盲，不是无限制地在推理时膨胀上下文。

现在来说实验。论文在七个软件创作领域上做了评估：幻灯片设计（PPT）、二维制图（CAD）、网页（HTML/CSS/JS）、电子表格（Excel）、三维场景（Blender）、实时三维（UE5）、音频制作（Reaper）。每个领域有一批经过人工筛选的任务描述，这些任务描述的生成过程是与技能库完全隔离的——生成任务的语言模型调用不接收任何技能标识符、维基列表或分类树信息，从源头上防止数据污染。

对比系统有四个：带技能的完整Resource2Skill流水线；不带技能的同款智能体；还有两个开箱即用的智能体框架——ClaudeCode和Codex的命令行版本，它们作为"强基线"。这两个框架没有接入任何技能库，也没有注入Resource2Skill特定的提示。测试了四个模型后端：GPT-5.5、GPT-5.4、GPT-5.4 Mini、GPT-5.4 Nano。评测是用语言模型担任评判，非音频工件用GPT-5.4视觉评判，Reaper音频工件用具有音频理解能力的GPT-4o系列评判。评判模型不知道是哪个系统产生的工件，只看到任务描述和渲染后的工件。每个领域有自己的五轴评分标准，比如Blender的轴是光照、构图、材质真实感、场景复杂度、整体美感；Web的轴是视觉设计、层级清晰度、内容丰富度、现代感、整体完成度。五轴分数的算术平均就是overall分数，以百分制报告。无法产出可评分工件的运行算零分并计入分母。

主要结果怎么样？带技能的Resource2Skill在所有模型与领域的组合格子里都打败了不带技能的基线，平均overall分数比无技能智能体高出若干个百分点——论文里原始数字因为格式原因有些被遮掉了，但明确写了"28个主要聚合格子里赢了26个"，以及"平均整体分数比无技能版本高出相应百分点"。两个例外情况——GPT-5.5在Web任务上输给了ClaudeCode、GPT-5.4 Nano在PPT任务上输给了Codex——差距都在一个百分点之内，基本可以视为统计噪声。配对Wilcoxon符号秩检验在每一个报告格子上都达到了统计显著性。

提升最大的地方是哪里？是那些操作惯例密集、从零推理成本极高的领域。Blender、Web、UE5的提升幅度最大，其中UE5的提升尤为突出——无技能的智能体在UE5上频繁无法组装出一个最低可用的场景，经常因为低于最低质量阈值而得零分，技能库的介入带来了非常显著的改善。Reaper的提升最小，反映了模型在音频制作这个领域的先验知识本来就相对足够。人工A/B评测用五位评分者对七个领域各30对匹配样本进行了盲评，Resource2Skill在所有七个领域的偏好方向上都得到了验证。

然后是缩放研究。固定智能体、评判模型和任务集，只改变开放给智能体的技能库大小，从零技能一路扩展到完整库。结果是每个领域的性能都随着库的规模单调递增，在接近某个数量之后开始趋于饱和。论文提到饱和点大约在某个中等规模之后，最终的"完整"步骤每个领域最多增加约两个百分点。早期进入库的技能覆盖的是通用操作和错误恢复流程，收益最大；后期进入的技能填补的是更细分的领域特定空白，边际收益递减。

在线获取研究比较有意思。对比了仅用离线库、以及离线库加在线获取两种条件，在两组任务集上测试：一组是正常的匹配基准，另一组是专门针对离线库已知覆盖不足的能力区域构造的压力测试集。结果非常清晰——在正常基准上，在线获取额外增加的分数约等于零，说明离线库已经足够覆盖常见请求；但在压力测试集上，在线获取把平均分从某个较低分数提升了若干百分点，说明它是一个有效的能力补盲工具，而不是一个通用的性能提升器。这就是为什么论文把默认设置定为仅离线模式——在标准评测上，你用在线获取只是在烧计算资源而没有收益。

消融实验揭示了哪些关键设计选择的贡献？一共有几组消融，我们一一来看。

第一组比较平铺文本库和有层级的维基。平铺文本库相对于无技能版本已经有提升，证明可复用的技能描述本身就有价值。但有层级的完整维基在每个领域都比平铺库更好，差距在若干百分点到十几个百分点之间，Excel、Web、Blender的差距最大。层级浏览缩小了搜索空间；代码字段和视觉字段提供了纯文本无法刻画的执行粒度。

第二组是来源消融，这是这篇论文最重要的消融之一。把视频资源去掉，只用代码加文章加工件——这时候平均分掉了不少，而且仅用视频的库还比三种来源但没有视频的库分更高。这说明视频是不可替代的来源。视频的缺失主要集中在操作时序和视觉序列承载重要信息的那些任务上，比如Excel和Web的下降都相当可观。在视频之外，没有哪种补充资源单独占据主导，但把所有四种资源组合起来始终比最强的两源组合多出一些分数——多样性带来了覆盖保险。

第三组是技能内容格式消融，这里是一个精心设计的匹配预算实验——所有条件共享相同的资源池、接受的技能ID、维基前置元数据、BM25加语言模型的检索预算，只有检索后暴露给智能体的内容格式不同：只有文本、加上视觉、加上代码、还是全部三种。结果是纯文本条件已经因为继承了适用性和路由线索而得到不错的分数，视觉字段再加上若干百分点，代码字段再加上若干百分点，完整的多模态格式排名第一。这个设计巧妙地隔离了"多模态内容本身的价值"和"精心策划的文本记忆的价值"——它证明了提升来自多模态内容本身，而不仅仅是有一个组织良好的文本库。

第四组是选择策略消融。在固定库、智能体、评判和候选预算的前提下，比较六种选择策略：MetaBrowse（层级加语言模型）、BM25词法检索、密集向量检索Embed、BM25加密集重排、随机从完整库抽样、以及无技能基线。MetaBrowse在每个领域都是最好的，平均分领先最强的纯检索基线若干百分点，差距最大的地方在Excel、PPT和Blender，说明任务适配性和技能互补性这些维度是词法或向量相似度无法捕捉的。

这篇论文有什么局限性？论文在案例研究部分诚实地列出了一些边界问题。一是部分落地问题，技能里的文本和视觉证据有时候只提供了局部的操作指导，没有完全解决参数绑定——也就是说智能体知道用哪个技能，但不完全知道具体参数该填什么。二是过于字面的组合，当多个技能被组合使用时，智能体有时候过于机械地拼接，没有做好适配。三是在某些领域，技能库的执行代码和真实环境的API版本之间存在兼容性问题。

对你的工作有哪些具体可借鉴之处？

如果你在做软件操作智能体或者任何形式的工具使用智能体，这篇论文最直接的启发是：不要只从智能体自己的轨迹里积累技能，人类创作的教程视频是一座几乎没有被开发过的富矿，而且它携带的信息密度——操作时序、视觉效果、专家惯例——是文本资料无法复制的。提炼而不是直接使用是关键动作，把视频变成结构化的、带可执行代码和视觉缩略图的技能条目，才能在推理时以合理的计算代价使用它。

其次，层级组织和两阶段选择的设计组合是一个值得复用的模式。如果你的技能库超过几百条，平铺检索的质量会明显下降，而把领域知识编码进分类树，再用词法评分粗筛加语言模型精选的两阶段策略，是一个在搜索效率和选择质量之间取得平衡的成熟方案。

第三，把在线获取设计成受控的能力补盲工具，而不是默认开启的全局增强，这是一个务实的工程决策。如果你的离线库已经覆盖了常见请求，在推理时无差别地做在线搜索只是在浪费计算和延长延迟，不会带来质量提升。只有在检测到能力覆盖不足时才触发在线获取，才是正确的使用姿势。

最后，多模态技能格式里的每一种模态都有独立贡献这一点，提示我们在设计知识表示时不应该轻易把某种模态降格为可选项。可执行代码给了智能体直接可用的工具调用模板，视觉材料给了智能体感知层面的参照，文本给了智能体理解适用场景的语义依据，三者缺一都会带来可测量的性能损失。这个认识对任何需要把外部知识注入智能体的系统都是直接适用的。

总结来看，Resource2Skill最核心的贡献是把"从多模态人类资源中提炼可执行技能"这件事变成了一个系统化的、可控变量的工程问题，而不是一个黑箱操作，并且用跨七个领域的受控实验证明了这条路线在实践中确实有效——对于任何正在构建面向复杂软件操作的智能体系统的人来说，这套框架的设计选择和实验方法都提供了扎实的参考起点。
