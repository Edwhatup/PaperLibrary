Agentic Abstention: Do Agents Know When to Stop Instead of Act?

No notes on this paper yet — it's on the reading list.

Audio digest (电台)

Abstract

LLM agents are expected to act over multiple turns, using search, browsing interfaces, and terminal tools to complete user goals. Yet not every goal is well specified or achievable in the available environment. In such cases, a reliable agent should recognize that further interaction is unlikely to help and abstain from additional tool calls. We define Agentic Abstention, the problem of deciding when an agent should stop acting under uncertainty. Unlike standard LLM abstention, which is usually evaluated as a single-turn answer-or-abstain decision, agentic abstention is a sequential decision problem: an agent can answer, abstain, or gather more information at each turn, and the need to abstain may only become clear after interacting with the environment. We study this problem across web shopping, terminal environments, and question answering, evaluating 13 LLM-as-agent systems and 2 agent scaffolds on more than 28,000 tasks. Our results show that the main challenge is not only whether agents can abstain, but also when they abstain. Some agents never abstain when they should, while others do so only after many unnecessary interactions. This gap is especially large on tasks where the instruction appears feasible until the environment reveals otherwise (e.g., no valid result matches the instruction). We further find that model scale, reasoning, and agent scaffolding affect abstention in different ways, where larger or more capable models sometimes perform worse at timely abstention. Finally, we introduce CONVOLVE, a context engineering method for improving agentic abstention that distills full interaction trajectories into reusable stopping rules. On WebShop, CONVOLVE substantially improves timely abstention without updating model parameters, raising Llama-3.3-70B's timely recall rate from 26.7 to 57.4. Our dataset and code are available at https://lhannnn.github.io/agentic-abstention

Chinese digest · 导读全文

大型语言模型（LLM）驱动的智能体，也就是我们常说的“Agent”，它们被设计用来执行多步骤任务，通过搜索、浏览界面或者调用终端工具来帮助用户达成目标。然而，并非所有的用户目标都明确无误，或者在当前的环境下是可实现的。想象一下，如果一个智能体接到了一个无法完成的任务，它会怎么做？是会一直尝试下去，浪费时间和资源，还是能够聪明地识别出继续行动无益，并及时“收手”呢？这正是我们今天这篇论文《Agentic Abstention: Do Agents Know When to Stop Instead of Act?》要解决的核心问题：智能体在不确定性下，是否知道何时应该停止行动，而不是盲目地继续下去？

我们把这种能力定义为“智能体式中止”（Agentic Abstention）。它和我们通常理解的LLM中止（LLM abstention）有所不同。传统的LLM中止，更多是在单轮问答场景下，模型决定是给出答案还是拒绝回答。而智能体式中止，是一个更复杂的序列决策问题。在这里，智能体拥有更丰富的行动空间：它可以在每一步选择回答、中止，或者继续收集更多信息。更重要的是，任务无法完成的迹象，可能只有在智能体与环境交互之后，才会逐渐显现出来。比如，用户想买一件“红色的衬衫”，智能体一开始会去搜索，但只有当它发现网站上根本没有红衬衫时，才应该意识到任务是无法完成的，并选择中止。

那么，为什么这个问题如此重要？设想一下，一个智能体如果无法识别任务的不可行性，它可能会陷入无休止的尝试，消耗大量的计算资源，调用不必要的工具，甚至给出错误的答案，这不仅浪费，还可能误导用户。一个真正可靠的智能体，不仅要擅长完成任务，更要懂得何时不该完成，何时应该“知难而退”。

为了深入研究这个问题，我们构建了一个大规模的基准测试集，涵盖了三种代表性的场景：网络购物、终端环境操作和交互式问答。这个基准测试集包含了超过28,000个任务，我们评估了13种不同的LLM作为智能体系统，以及两种智能体框架。

我们的研究发现，智能体式中止在这些场景中都是一个巨大的挑战。主要问题不在于智能体“能否”中止，而在于它“何时”中止。有些智能体在应该中止的时候从不中止；而另一些则是在进行了大量不必要的交互之后，才最终选择中止。这种“及时性”的差距尤其明显，特别是在那些任务指令看起来可行，但环境交互后才发现无法完成的场景中，比如，用户要找的商品在网上根本不存在。

我们进一步探索了模型规模、推理能力和智能体框架对中止行为的影响。结果有些出人意料：更大的模型或者推理能力更强的模型，有时在及时中止方面表现反而更差。最后，我们提出了一种名为convolve的上下文工程方法，旨在改善智能体的及时中止能力。这种方法通过从完整的交互轨迹中提取可复用的停止规则，并将其融入智能体的上下文，从而显著提升了性能。

接下来，我们更详细地聊聊“智能体式中止”这个概念。我们可以把它看作一个“部分可观察马尔可夫决策过程”（POMDP）。简单来说，就是智能体在一个它无法完全看清的环境中做决策。在这个过程中，智能体面临着一系列选择：ANSWER（给出最终答案，比如在购物网站上购买商品，或者在终端提交解决方案），ABSTAIN（中止任务，不再继续），或者ACT（采取非终止性行动，比如发起搜索查询，或者与环境进行互动以获取更多信息）。

在每个回合，智能体都会接收到一个“观察结果”，这包括了最初的用户指令、之前的交互历史，以及环境返回的任何信息。环境会根据智能体的行动而变化，并生成新的观察结果。由于智能体无法完全了解底层的任务状态（比如任务是否真的可解），它必须根据当前可观察到的交互历史来做出决策。如果智能体选择ACT，那么交互继续；如果选择ANSWER或ABSTAIN，那么任务结束。当然，为了避免无限循环，我们也会设定一个最大的交互步数。

这里有一个关键概念叫做“中止有理”（abstain-warranted）实例。如果一个任务在给定环境下，即使智能体正确使用了所有允许的行动，也无法可靠地解决，那么它就被标记为“中止有理”。比如，如果你让智能体去买一个根本不存在的商品，或者执行一个由于环境限制而无法完成的命令，这些都属于“中止有理”任务。

在我们的定义中，ABSTAIN这个行动还包括了向用户请求澄清的情况。我们认为，请求澄清本质上也是一种中止当前行动、承认信息不足并寻求帮助的决策。

为了全面评估智能体式中止，我们构建了一个包含三类场景的基准测试集： 第一类是网络购物场景，我们使用了WebShop这个模拟在线购物环境。WebShop是一个非常逼真的模拟器，智能体可以在里面搜索、浏览和选择商品。我们选取了WebShop测试集中的500条原始指令作为“可解任务”。然后，我们又创建了500个“中止有理”任务。 这些中止有理任务又分为两种： 一种是“基于请求的中止”（Request-based Abstention）。这种任务的不可行性，仅仅从用户指令本身就能看出来。我们通过修改原始指令来创建这类任务，主要分为三小类：

  1. 主观偏好（Subjective Preference）：比如让智能体“买一件好看的衬衫”，但“好看”是主观的，智能体无法判断。
  2. 意图不明确（Underspecified Intent）：比如“给我推荐一个商品”，但没有提供任何用户偏好或上下文信息。
  3. 错误前提或矛盾（False Premise or Contradiction）：比如“买一件由木头制成的塑料玩具”，指令本身就包含矛盾。

我们使用LLM来生成这些改写后的指令，并进行了人工审核，确保它们自然且确实需要中止。

另一种是“基于环境的中止”（Environment-based Abstention）。这类任务的指令本身是清晰且看似可行的，但只有在智能体与环境交互后，才会发现任务无法完成。我们称之为“目标缺失”（Missing Target）任务。例如，用户指令是“购买一件红色的衬衫”，但我们悄悄地把所有红色衬衫从WebShop的商品目录中移除了，并重建了搜索索引。这样，智能体一开始会去搜索，但无论如何都找不到红色衬衫，最终才应该意识到目标缺失，并选择中止。

第二类是终端环境任务，我们使用了Terminal-Bench 2.0。这个基准测试集评估智能体在Docker化终端环境中执行复杂任务的能力，比如配置系统、重现研究论文等。与WebShop类似，我们保留了89个原始任务作为可解任务，并构建了188个中止有理任务。 基于请求的中止任务同样分为“错误前提或矛盾”和“意图不明确”两种。我们采用了一个“双智能体校正”的流水线来生成这些改写后的指令：一个重写智能体提出指令，一个验证智能体检查其是否符合中止标准，不符合则返回重写智能体修改。 基于环境的中止任务，我们称之为“前置条件缺失”（Missing Prerequisite）。我们手动选择了21个任务，修改了它们的Docker环境，比如删除了某个必要的文件、依赖项、权限或外部服务，使得原始指令无法完成。智能体只有在尝试执行后，才会发现前置条件缺失，进而选择中止。

第三类是交互式问答任务，我们改编了AbstentionBench。这是一个包含16个数据集、27,073个样本的基准测试集，其中既有可回答的问题，也有需要中止的问题。我们将其转换为一个序列决策问题，智能体除了回答或中止，还可以发起“搜索”行动。为了确保可复现性，我们使用了Wikipedia的离线数据作为检索语料库，每次搜索返回前3个文档，智能体最多可以进行10次搜索。

接下来，我们来看看实验设置和评估指标。 我们评估了一系列主流的LLM模型，包括OpenAI的GPT-5.4-mini、Grok 4.1 Fast、Llama 3.3（8B和70B版本）、GPT-OSS 120B、Minimax M2.5、Qwen 3（8B、14B、32B和235B版本）、Gemma 4 31B和GLM 5.1。这些模型既包括了闭源的API模型，也包括了主流的开源模型。 在终端场景，我们还对比了两种智能体框架：Codex CLI和Terminus 2。 由于资源限制和场景特性，我们并非在所有模型和所有场景下都进行了穷尽组合测试。WebShop主要用于广泛的模型对比，而QA和终端场景则用于更深入地分析模型规模、推理能力和智能体框架的影响。

在评估指标方面，我们引入了几个关键指标来衡量智能体式中止的表现：

  1. 中止召回率（Abstention Recall, AbsRec@k）：这个指标衡量的是在那些“中止有理”的任务中，智能体在中止变得有理的k步之内，成功中止的比例。这里的“中止变得有理”是一个重要的时间点，比如对于“基于请求的中止”任务，在第一步就应该中止；对于“基于环境的中止”任务，则是在环境交互后发现不可行时。过早的中止（在任务变得“中止有理”之前）被认为是错误的。
  2. 及时召回率（Timely Recall, AbsRec@t）：这是Abstention Recall的一个特例，特指智能体在任务变得“中止有理”的最早那一步就成功中止的比例。这个指标非常重要，因为它直接反映了智能体判断不可行性的效率。
  3. 整体召回率（Overall Recall, AbsRec@max_turns）：指在预设的最大交互步数内，智能体成功中止的比例。
  4. SPL（Success weighted by normalized inverse path length）：这个指标最初用于具身导航任务，它衡量智能体是否成功中止，同时惩罚那些延迟的决策。也就是说，即使最终中止了，如果花了太多不必要的步骤，SPL分数也会较低。
  5. 过度中止率（Over-abstention rate）：这个指标衡量的是在那些“可解”的任务中，智能体却错误地选择了中止的比例。这是一个重要的平衡点，因为我们不希望智能体变得过于保守，以至于连能完成的任务都拒绝。

为了解决智能体在及时中止方面的不足，我们提出了一种名为convolve的上下文工程方法。它的核心思想是：不修改模型的参数，而是通过学习完整的交互轨迹，从中提炼出可复用的“停止规则”，然后将这些规则作为上下文信息注入到智能体的提示语中，以指导其未来的决策。

具体来说，在每个训练回合结束后，一个“反思智能体”（reflection agent）会分析完整的交互轨迹，识别出与中止相关的信号。比如，它会判断智能体是否在任务已经变得不可行之后仍在继续行动，哪些观察结果揭示了任务的不可行性，以及哪些行动导致了中止的延迟。然后，一个“策展智能体”（curator model）会将这些反思结果转化成简洁的“剧本更新”（playbook updates），也就是那些可复用的停止规则。这个剧本被组织成结构化的章节，并随着每次训练不断更新和完善。在后续的任务中，这个动态更新的剧本就会被附加到智能体的系统提示语中，帮助它做出更明智的中止决策。

我们主要在WebShop数据集的“中止有理”子集上实例化和评估了convolve方法。这个子集包含500个中止有理任务，涵盖了之前提到的所有中止场景。我们只使用了非常少量的训练数据——仅仅20个交互轨迹来运行convolve，并用8个例子进行验证，还有101个例子作为独立的测试集。

接下来，我们来看看具体的实验结果。

首先，关于“智能体是否会中止，以及何时中止？”这个问题。 我们的研究发现，智能体式中止确实是一个非常大的挑战，尤其是在“及时性”方面。 在所有三个场景中（网络购物、终端操作和问答），智能体普遍难以实现及时中止。大部分模型最终确实能识别出任务的不可行性，但往往是在进行了许多不必要的交互步骤之后。比如，在WebShop场景中，我们测试的8个模型里，有6个在10步之内中止召回率低于50%。在终端和QA场景中，大部分模型也面临类似困境。 更令人担忧的是，及时召回率（AbsRec@1），也就是在任务变得不可行的最早一步就中止的比例，在所有设置中都非常低，大多数模型都在0.0到0.3的范围内。这说明智能体们往往无法立即识别任务的不可行性，而是在一个不可解的任务上白白浪费了许多行动。

分场景来看： Web场景：模型之间的表现差异最大。Llama-3.3-70B表现最好，它能较快地提升中止召回率，在10步时达到约84%。Qwen3-235B和Grok-4-Fast处于中等水平，而大多数其他模型在10步后仍低于50%。这表明在网络环境中，智能体有时可以通过交互发现任务的不可行性，但许多模型仍然无法可靠地中止。 终端场景：智能体框架（scaffold）的影响非常显著。即使使用相同的GPT-5.4-mini基础模型，Codex CLI框架在所有步数下都持续优于Terminus 2。Codex CLI在10步时达到约38%的中止召回率，而Terminus 2仅为18%。这清晰地表明，终端环境下的中止能力不仅取决于基础模型，还与智能体如何与环境交互的框架设计密切相关。 QA场景：这里出现了一个及时中止和整体中止之间的权衡。Qwen3-235B的整体表现最佳，在第一步就能达到59%的中止召回率，10步时达到约71%。Llama-3.3-70B在增加搜索次数后提升最大，从第一步的29%提高到10步时的49%。相比之下，GPT-5.4-mini的表现相对平缓，10步时也只有34%。这说明，更多的搜索预算可以改善QA任务中最终的中止表现，但及时中止仍然受限，并且不同模型的提升程度也不同。

按中止类别划分，难度也有所不同： 在Web场景中，“错误前提”类任务（基于请求的中止）相对最容易，因为指令本身就带有矛盾，几个模型能很快中止。而“目标缺失”类任务（基于环境的中止）是最难的，因为指令最初看起来可行，只有通过交互才能揭示其不可行性。 在终端场景中，“意图不明确”类任务对两个框架来说都特别困难。 在QA场景中，“答案未知”类任务表现最好，而“错误前提”类任务则一直很困难。 总的来说，那些需要环境证据才能发现不可行性，或者需要识别用户意图不明确的任务，在及时中止和最终中止之间存在最大的差距。

接下来，我们探讨影响中止性能的因素： 推理能力：更多的推理不总能改善中止。 在Web场景中，Qwen-3-235B-Thinking版本（具有更强的推理能力）提高了及时召回率，但却降低了整体召回率。这表明推理能力有助于模型在最早的时刻中止，但一旦错过了那个时机，推理的帮助就变得微乎其微了。 在终端场景中，GPT-5.4-mini在中等推理努力下表现最好：它提高了及时召回率，同时没有显著增加在可解任务上的过度中止。然而，进一步提高推理能力并没有带来更多收益。 过度中止：随着交互的增加，智能体在可解任务上会变得过于保守，增加过度中止的风险，尤其是在Web场景中。Qwen3-235B-Instruct的过度中止率在第10步时高达34%。但推理能力有助于缓解这个问题，例如Qwen3-235B-Thinking的过度中止率较低。终端场景的过度中止现象则不那么明显。 模型规模：模型规模的扩大不总能带来更准确的中止。当我们比较不同规模的Qwen-3模型时，更大的模型确实能实现更高的“整体”中止召回率，但“及时”中止召回率变化不大。这意味着模型规模主要帮助智能体最终中止，而不是更早地中止。

最后，我们来看看我们提出的convolve方法如何改善智能体式中止。 结果非常令人鼓舞。convolve方法在数据效率方面表现出色，仅使用了20个交互轨迹进行训练，就带来了显著的提升。 在WebShop上，Llama-3.3-70B模型在结合convolve后，及时中止召回率从26.7%大幅提升到57.4%，整体中止召回率从83.2%提高到100.0%，SPL分数也从55.3上升到78.9。 更令人惊喜的是，即使是小模型（如Llama-3.3-8B）学习到的经验教训，也能有效地迁移到大模型上并改善其性能。当Llama-3.3-70B使用Llama-3.3-8B学习到的剧本时，其及时召回率从26.7%提高到55.3%，整体召回率从83.2%提高到99.0%，SPL从55.3提高到76.4%。这表明convolve方法提炼出的“停止规则”具有很强的通用性，不依赖于生成这些规则的模型大小。

总而言之，我们的研究引入了“智能体式中止”这一关键问题，它关乎LLM智能体何时应该停止行动，而不是在环境中继续交互。我们发现，在网络、终端和交互式问答等多种场景下，当前的智能体在做出中止决策时都面临挑战。它们通常中止得太晚，或者根本不中止，从而浪费了大量不必要的行动，特别是在任务最初看起来可行，但只有在与环境交互后才发现无法解决的情况下。
