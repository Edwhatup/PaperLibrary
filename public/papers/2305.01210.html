Audio digest (电台)

Abstract

Program synthesis has been long studied with recent approaches focused on directly using the power of Large Language Models (LLMs) to generate code. Programming benchmarks, with curated synthesis problems and test-cases, are used to measure the performance of various LLMs on code synthesis. However, these test-cases can be limited in both quantity and quality for fully assessing the functional correctness of the generated code. Such limitation in the existing benchmarks begs the following question: In the era of LLMs, is the code generated really correct? To answer this, we propose EvalPlus -- a code synthesis evaluation framework to rigorously benchmark the functional correctness of LLM-synthesized code. EvalPlus augments a given evaluation dataset with large amounts of test-cases newly produced by an automatic test input generator, powered by both LLM- and mutation-based strategies. While EvalPlus is general, we extend the test-cases of the popular HumanEval benchmark by 80x to build HumanEval+. Our extensive evaluation across 26 popular LLMs (e.g., GPT-4 and ChatGPT) demonstrates that HumanEval+ is able to catch significant amounts of previously undetected wrong code synthesized by LLMs, reducing the pass@k by up-to 19.3-28.9%. We also surprisingly found that test insufficiency can lead to mis-ranking. For example, both WizardCoder-CodeLlama and Phind-CodeLlama now outperform ChatGPT on HumanEval+, while none of them could on HumanEval. Our work not only indicates that prior popular code synthesis evaluation results do not accurately reflect the true performance of LLMs for code synthesis, but also opens up a new direction to improve such programming benchmarks through automated testing. We have open-sourced our tools, enhanced datasets as well as all LLM-generated code at https://github.com/evalplus/evalplus to facilitate and accelerate future LLM-for-code research.

我们今天要聊的这篇论文，直接切入了当前大语言模型生成代码领域的一个核心痛点：那就是我们到底应该如何严谨地评估这些模型生成的代码是否真的正确。大家知道，现在像ChatGPT这样的AI模型，已经能写出各种各样的代码了，而且很多时候看起来还挺像样。但是，这些代码真的能完美运行，覆盖所有边界情况吗？这篇论文的标题就直接抛出了这个问题：“ChatGPT生成的代码真的正确吗？对大语言模型代码生成进行严格评估”。

长久以来，程序合成一直是计算机科学领域一个非常重要的研究方向。过去几十年，我们发展出了很多经典的程序合成技术，比如基于演绎的合成、基于归纳的合成，还有后来神经引导的合成等等。但是，随着大语言模型，也就是我们常说的LLM的兴起，以及开源代码库的爆炸式增长，研究人员开始把目光聚焦到直接利用LLM来生成代码上。像OpenAI的Codex和CodeGen这样的模型，它们通过自回归的方式，根据函数签名和文档字符串这些上下文信息，预测下一个代码片段，最终生成一个完整的函数来满足用户的需求。凭借它们强大的自然语言理解能力和代码生成能力，这些模型在代码合成任务上展现出了令人惊叹的性能。

然而，这里面有一个最核心的担忧，就是这些LLM生成的代码到底对不对。传统的自然语言处理指标，比如BLEU分数，在评估代码时就不那么可靠了，因为两段看起来完全不同的代码，在功能上可能却是等价的。理想情况下，我们当然希望能够形式化地验证LLM提供的代码方案，确保它在任何输入下都绝对正确。但是，即使是针对特定领域的程序，进行形式化验证也已经非常困难了，更别说要构建一个通用的验证器，能够绝对准确地证明代码基准测试中的各种问题。所以，目前大家在评估LLM生成的代码时，主要还是依赖于手工构建的测试用例。

问题就出在这里了。这些现有的测试用例，往往数量有限，而且质量也参差不齐，很难全面捕捉到所有可能的情况。因为要精心设计高质量的测试用例，本身就是一项非常耗时费力的工作。所以，这篇论文就提出，现有的编程基准测试，对于评估LLM生成的代码的实际正确性来说，是远远不够的，甚至可能导致我们对结果产生一种虚假的信心。

具体来说，作者们指出了现有LLM代码生成基准测试的两个主要局限性：

第一个是测试不足。目前的编程基准测试，平均每个编程问题只包含不到十个测试用例。而且，这些测试用例通常相对简单，不足以充分探索代码的所有功能或者各种边界情况。论文中举了一个很有意思的例子：ChatGPT生成了一段代码，目的是返回两个列表中排序后的唯一公共元素。这段代码乍一看似乎是正确的，用HumanEval基准测试自带的几个简单输入去跑，也能得到预期的结果。但是，它在返回语句中，把一个中间的列表错误地转换成了一个集合。我们知道，集合是无序的，这样一来，就破坏了之前排序好的顺序。你看，这样一个逻辑上有缺陷的解决方案，却能通过所有简单的测试，被误认为正确，这就是因为测试用例太少了，不够充分。

第二个是问题描述不精确。代码生成任务的输入，除了函数签名，还包括自然语言描述，也就是我们常说的文档字符串。现有基准测试中的这些任务描述，很多时候都太过模糊，没有完全澄清程序应该有的行为。比如，输入文档字符串可能没有明确指定预期的输入范围，比如说只允许正整数，或者函数应该如何处理异常情况。结果就是，LLM可能会对这些编程问题有不同的解读，从而导致那些本来能力很强的LLM，在评估时反而被误判为能力不足。

这些局限性在许多流行的代码生成基准测试中都普遍存在，这不仅让人对之前那些声称LLM性能惊人的研究结果产生了质疑，也为我们如何正确评估LLM代码生成器提出了一个严峻的挑战。所以，这篇论文的核心目标，就是解决这个根本性的评估难题，并提出一个反思性的问题：LLM生成的代码真的正确吗？

为了回答这个问题，作者们提出了EvalPlus——一个全新的评估框架，旨在改进现有的代码基准测试，从而更精确地评估LLM生成代码的功能正确性。EvalPlus的核心是一个自动化测试输入生成引擎。它通过生成大量有意思的测试输入，来扩充现有代码基准测试，从而充分地测试代码解决方案，并通过与“黄金标准”也就是参考实现进行交叉检查，来验证其功能正确性。

EvalPlus在测试用例生成上，采用了两种策略相结合的方式：一种是基于大语言模型的策略，另一种是基于变异测试的策略。

首先，EvalPlus会利用ChatGPT来生成一组高质量的“种子输入”。这些种子输入旨在测试程序中那些困难的边界情况和复杂的功能，并且要符合有效的输入结构。为什么要用ChatGPT呢？因为ChatGPT具有强大的理解能力，它能够通过检查参考实现，学习到有效的输入格式，比如变量类型，以及参考实现所期望的功能，从而生成出有意义的测试输入，这些输入能够有效地揭示不正确代码中的bug。比如，某些编程问题可能要求输入符合特定的语义约束，比如要求输入是一个回文串。这种语义约束对于传统的输入生成器来说是非常难以满足的，但ChatGPT却能很好地处理。

当然，ChatGPT虽然厉害，但用它来大规模地自动化生成测试用例，速度和成本上都不划算。为了解决这个问题，EvalPlus在生成了高质量的种子输入之后，会接着进行“类型感知输入变异”。这是一种基于变异测试的模糊测试工作流。它会从种子输入池中随机选择一个输入，然后对其进行变异，生成新的输入，也就是“变异体”。这些新的输入，如果符合程序的契约，也就是预设的输入条件，就会被添加到种子输入池中，然后这个过程不断循环，从而高效地生成大量的测试输入。

“类型感知变异”是什么意思呢？它会检查现有有效种子输入的数据类型，然后生成与这些种子在结构上相似的新输入。比如，对于像整数和浮点数这样的基本类型，变异操作可能只是简单地增加或减少数值。而对于像列表、字典这样的复合类型和字符串类型，除了常见的删除或重复现有元素或子字符串之外，其中的元素和子字符串还可以根据它们的内部类型进行递归变异。这些子变异体可以用来替换现有项或添加新项，实现更细粒度的变异。此外，为了避免生成那些违反微妙语义约束的输入，EvalPlus还引入了一种“成分机制”，它会收集出现过的数据片段，并在变异过程中重复使用它们。简而言之，类型感知输入变异在ChatGPT生成的高质量种子输入的基础上，能够生成大量测试输入，这些输入将作为最终的全面测试集，用于评估LLM生成的代码。

生成了这么多测试用例之后，EvalPlus会通过“差分测试”的方式来评估LLM生成的代码。差分测试的原理很简单：就是把LLM生成的代码和“黄金标准”也就是参考实现，用相同的测试输入去运行，然后比较它们的输出。如果输出不一致，就说明LLM生成的代码有问题。

这么多测试用例，虽然能有效地发现错误代码，但执行起来也会很耗时。所以，EvalPlus还提供了一个可选的功能，就是“测试套件精简”。它的目标是选择原始测试套件的一个子集，同时仍然保持与原始测试套件相同的测试效果。要实现测试精简，通常需要假设每个测试用例都能满足一系列“测试要求”。这个问题可以被形式化为集合覆盖问题。为了有效地解决这个问题，准确定义测试要求至关重要。在这篇论文中，作者们关注了以下几种测试要求：

第一种是代码覆盖率。代码覆盖率衡量的是每个测试用例执行了多少代码元素，比如语句或分支。这在实践中被广泛用于衡量测试效果。这里的目标是只保留一个最小的测试子集，它能覆盖与完整测试集相同的分支集合。

第二种是变异杀伤。代码覆盖率衡量了代码被执行的程度，但高覆盖率的测试用例并不一定能有效发现代码中的关键缺陷。所以，研究人员提出了“变异测试”，也叫变异分析，来更精确地评估测试效果。变异测试通过对被测程序应用一系列预定义的变异规则，比如把“大于”改成“小于”，来创建大量人工的、有缺陷的程序，每个程序都包含一个微妙的bug，我们称之为“变异体”。这样，测试用例检测到的变异bug的比例，就可以用来评估测试效果。研究表明，变异测试在评估测试效果方面，可以大大优于代码覆盖率。所以，EvalPlus也会利用每个测试用例所杀死的变异体集合作为测试要求。目标是最小化测试用例的数量，同时仍然能够检测到相同数量的变异bug。

第三种是LLM样本杀伤。不同的LLM可能会在某些测试用例上普遍失败。所以，除了前面两种理论指标，作者们还使用了一种经验性的指标，叫做“样本杀伤”，也就是一个测试用例能够检测并证伪的错误LLM样本集合。当然，对于正在评估的新的LLM，我们还没有它的代码样本的执行结果。因此，这里只使用其他LLM生成的样本的执行结果来评估测试精简的效果。通过这种方式，目标是最小化测试用例的数量，同时确保其他模型生成的所有不正确样本都能被精简后的测试套件检测到。

除了这三种策略，作者们还研究了将所有三种测试要求合并起来进行精简的策略。也就是说，目标是最小化测试用例的数量，同时保持相同的分支覆盖率、变异杀伤和不正确样本检测结果。

最后，EvalPlus还引入了“程序输入契约”的概念。评估代码合成的目标是检查合成的代码是否准确反映了用户意图。这通常通过使用多个测试输入，并将生成代码的输出与参考实现的输出进行比较来完成。前面我们讨论了如何改进测试输入以更严格地评估合成代码。然而，这些用户意图，通常以自然语言文档字符串的形式表达，对于LLM来说可能过于模糊。因此，LLM可能会对所需功能、输入格式以及如何处理边界情况有不同的解释。为了解决这个问题，EvalPlus采用了“契约式编程”的理念，通过以代码断言的形式系统地标注函数前置条件，比如“assert n > 0”，来确保函数的测试输入是格式良好的。这些契约的好处有两方面：第一，它们可以补充自动输入生成步骤，过滤掉任何违反契约的无效输入。因为这些格式错误的输入可能导致未定义的行为，不适合用于评估LLM生成的代码。第二，它们可以作为与提示中的自然语言描述正交的描述符，提供进一步的澄清。

讲完了方法，我们来看看实验结果。

在实验设置上，作者们使用了无偏的pass@k指标来准确评估LLM生成代码的功能正确性。为了保证结果的通用性，他们对26个流行且最先进的LLM进行了全面评估，并使用了各种温度设置。具体来说，他们为每个模型随机抽样生成了200个程序样本，针对四个温度设置进行了实验，还进行了贪婪搜索解码。对于随机抽样，他们展示了每个k值下表现最佳的pass@k分数及其对应的温度。对于贪婪解码，他们只为每个任务合成一个确定性样本，并评估其通过率作为pass@1。由于时间和成本限制，GPT-4只在贪婪解码下进行了评估，而ChatGPT除了贪婪解码外，还在0.8温度下进行了随机抽样评估。

EvalPlus主要聚焦于评估HumanEval基准测试的有效性，因为HumanEval是代码生成领域使用最广泛的数据集之一。HumanEval包含164个人工编写的编程任务，每个任务都提供一个Python函数签名和文档字符串作为LLM的输入。LLM根据这些输入完成一个解决方案，其功能正确性由少数几个手动测试用例来判断。EvalPlus将HumanEval转换成了HumanEval+，它增加了超过100万个独特的测试用例，并修复了HumanEval中不正确的参考实现。具体来说，对于每个任务，EvalPlus基于大约30个ChatGPT生成的种子输入（通过3个独立的提示生成），运行类型感知变异，在一个小时内生成了1000个额外的输入。在HumanEval+中，164个编程任务中有83个被标注了手工编写的契约。

因为EvalPlus需要参考实现来交叉检查LLM生成的代码，所以确保参考实现的正确性至关重要。然而，通过检查原始HumanEval中的参考实现，作者们发现其中有超过10%的实现是错误的。因此，作为另一个贡献，他们仔细地重新实现了HumanEval+的所有参考实现，并进行了测试。

为了加快评估速度，他们还构建了HumanEval+-mini，这个版本比HumanEval+小了98%，但在所研究的模型上仍然保持了相似的测试效果。

现在来看看LLM的评估结果。论文中的表3展示了使用原始HumanEval和HumanEval+评估LLM时的pass@k结果。首先，一个非常显著的发现是，在所有LLM、模型大小和k值下，使用HumanEval+进行评估时，几乎所有pass@k结果都比使用原始HumanEval时显著下降。值得注意的是，性能下降幅度非常大，在不同k值下，下降幅度高达19.3%到28.9%。这种性能下降不仅出现在流行的开源LLM中，比如广泛使用的CodeGen-16B、CodeLlama-34B和StarCoder，也出现在最先进的商业模型ChatGPT和GPT-4中。

这些结果充分证实了作者们的假设：之前对HumanEval的评估不够鲁棒，无法检测到LLM合成的错误代码。由于这些LLM在日常编程中被广泛使用，并且是评估新代码合成技术的常见参考点，因此，作者们强烈建议在更鲁棒的基准测试，如HumanEval+上进行评估，以便得出精确的结论。

更令人惊讶的是，更严格的评估可能会得出不同甚至完全相反的相对排名结果。例如，在原始HumanEval上，WizardCoder-CodeLlama和Phind-CodeLlama在pass@1指标上被评估为不比ChatGPT好。然而，HumanEval+的结果表明，这两个开源模型实际上可以超越专有的ChatGPT。其他一些通过HumanEval+纠正的排名例子包括SantaCoder-1B超越了InCoder-6.7B，以及Vicuna-7B超越了InCoder-1.3B。

论文还展示了不同k值下最佳温度的分布情况。结果与之前的发现一致，即较低的温度通常对较小的k值表现更好，而较高的温度对较大的k值效果更好。他们还观察到，使用HumanEval+前后，最佳温度似乎保持了相当的一致性；然而，仍然存在细微的差异，例如，CodeGen-2B在pass@1上的最佳温度在使用HumanEval+后从0.8变为0.2。这促使未来的研究更密切地关注温度对评估测试鲁棒性的影响，特别是那些边界情况。

接下来是测试套件精简的有效性。HumanEval+平均每个编程任务有764.1个测试用例。通过测试套件精简器，他们将其最小化为HumanEval+-mini，每个任务只有16.1个测试用例，数量减少了98%。论文中的表4展示了对部分代表性模型进行留一交叉验证后的pass@k差异。结果显示，精简后的测试套件HumanEval+-mini几乎可以实现与HumanEval+相同的pass@k下降幅度，但使用的测试用例数量却少得多。

更深入地看，单独对每个指标进行集合覆盖，可以在一定程度上提高原始HumanEval的通过率。具体来说，使用经验性的LLM样本杀伤是最有效的，其效果与完整方法相同，但消耗的测试用例也比其他理论指标更多。虽然在样本杀伤之外，使用覆盖率和变异分析似乎并非必要，但它们仍然为理论上的测试充分性提供了基本保证。

论文还分析了通过率的分布。图3展示了每个编程任务在HumanEval和HumanEval+测试上的总体通过率。HumanEval和HumanEval+之间的通过率差距表明，HumanEval+能够检测到HumanEval在各种难度问题上误判为正确的解决方案。他们还观察到HumanEval中的问题并非都一样，不仅在问题难度上，而且在生成反例和边界情况以深入测试LLM生成代码的难度上也有所不同。对于“两数相加”和“字符串长度”这样的简单问题（通过率最高的两个问题），LLM很容易解决，人工测试也容易。而处理多个条件（例如“单词拆分”）、完整性（例如“判断素数”时处理负数）、推理能力（例如“斐波那契数列”）和效率要求（例如“第n个质数斐波那契数”）的问题，对于所评估的LLM来说是最困难的任务，这为未来改进LLM以掌握这些编码技能指明了方向。

除了检测LLM生成的错误代码，作者们还发现，即使是HumanEval原始的参考实现中，也存在18个缺陷，占所有问题的11%。这些缺陷包括：未处理的边界情况（5个），即之前的参考实现未能处理空列表或空字符串等边界输入；逻辑错误（10个），即之前的参考实现错误地实现了所需功能；以及性能问题（3个），即低效的实现导致在合理大小的输入上性能缓慢。其中，逻辑错误是最严重的问题，因为原始的“黄金标准”未能准确反映用户意图。这些缺陷也是通过差分测试发现的，但这次比较的是作者们自己重新实现的参考实现与HumanEval中的原始参考实现。

论文中举了一个“验证日期”的例子，这是一个被归类为逻辑错误的原始参考实现。这个任务是检查输入日期格式是否正确。原始实现的核心逻辑是先检查月份条件，然后处理相应的日期条件。但是，它的实现是错误的，因为Python中的“and”运算符优先级高于“or”运算符，导致原始函数检查的是“任一条件满足”，而不是“两个条件都必须满足”。这个错误通过自动生成的测试输入“12-31-1999”暴露出来，原始实现错误地将其标记为无效日期。令人惊讶的是，这个严重的错误在HumanEval的任何基础测试输入中都没有被发现，这进一步证明了原始测试输入的弱点和有限的评估能力。

总结一下，这篇论文提出了EvalPlus——一个由自动化测试生成驱动的严谨的程序合成评估框架。EvalPlus结合了LLM和基于变异的输入生成技术，以获取多样化的测试输入，从而准确评估LLM生成代码的正确性。EvalPlus创建了HumanEval+，它在流行的HumanEval基础上，增加了大量高质量的、自动生成的测试输入。通过测试套件精简，EvalPlus还生成了HumanEval+-mini，它比HumanEval+小了98%，但保留了相似的测试效果。

作者们对各种LLM进行了广泛评估，结果表明HumanEval+能够识别出大量之前未被发现的LLM生成的错误代码，证明了其在增强编程基准测试以实现更准确评估方面的有效性。自推出以来，EvalPlus的PyPI包在五个月内已被安装超过6000次。他们还持续评估新的代码模型，并在其网站上维护了一个排行榜。

未来，作者们计划将EvalPlus应用于MBPP等更多代码基准测试，以提供更高质量的测试。同时，未来的工作还可以探索如何将EvalPlus与更形式化的验证技术，比如Dafny，或者验证技术，比如翻译验证，相结合，以在适用时为评估结果提供更强的保证。此外，EvalPlus背后的核心测试生成技术甚至可以用于在进行AI结对编程时，例如使用Copilot，提醒开发者注意LLM生成的代码片段中可能存在的潜在缺陷。

这篇论文的结论和启发是：我们不能盲目相信大语言模型生成的代码，现有的评估方式存在严重不足。EvalPlus提供了一个更全面、更严谨的评估框架，它不仅揭示了当前LLM代码生成能力的真实水平，也为未来如何构建更可靠的AI代码辅助工具指明了方向。对于我们自己的研究，这意味着在依赖LLM生成代码时，必须投入更多的精力在测试和验证上，不能仅仅满足于通过几个简单的测试用例，而是要考虑引入自动化测试生成和契约式编程等技术，来确保代码的真正正确性。
