Evaluating Large Language Models Trained on Code

Audio digest (电台)

Abstract

We introduce Codex, a GPT language model fine-tuned on publicly available code from GitHub, and study its Python code-writing capabilities. A distinct production version of Codex powers GitHub Copilot. On HumanEval, a new evaluation set we release to measure functional correctness for synthesizing programs from docstrings, our model solves 28.8% of the problems, while GPT-3 solves 0% and GPT-J solves 11.4%. Furthermore, we find that repeated sampling from the model is a surprisingly effective strategy for producing working solutions to difficult prompts. Using this method, we solve 70.2% of our problems with 100 samples per problem. Careful investigation of our model reveals its limitations, including difficulty with docstrings describing long chains of operations and with binding operations to variables. Finally, we discuss the potential broader impacts of deploying powerful code generation technologies, covering safety, security, and economics.

Chinese digest · 导读全文

如何让语言模型真正学会写代码，这是这篇论文要解决的核心问题。

在2021年这篇论文发表之前，大家已经知道GPT-3这类大型语言模型能生成一些简单的代码片段，但它到底能不能写出功能正确、能运行、能通过测试的代码，没有人系统地研究过。更重要的是，当时甚至没有一个好的评测标准——研究者们评价代码质量用的是BLEU分数，这个指标原本是给机器翻译设计的，看的是生成文本和参考答案有多像，但代码不是这么回事：两段代码可以长得完全不一样，却实现完全相同的功能，反过来，两段代码可以看起来很像，但一个能跑通，另一个藏着致命的逻辑错误。

所以这篇论文做了两件核心工作：一是训练了一个专门用于写代码的模型，叫Codex；二是提出了一套新的评测体系，叫HumanEval。这两件事放在一起，构成了整个研究的骨架，而这个工作也是后来GitHub Copilot的直接前身。

先讲评测这件事，因为它其实比模型本身更有开创性。

研究团队手工写了164道编程题，每道题包含函数签名、文档字符串，也就是docstring，还有平均7.7个单元测试。评测的方式很直接：给模型看函数签名和docstring，让它写出函数体，然后运行单元测试，看能不能通过。能通过就算对，不能通过就算错。这种方式叫"功能正确性评测"，完全绕开了"长得像不像"的问题，直接问"能不能用"。

这164道题是研究人员自己手写的，这一点很关键。因为模型是在GitHub上训练的，如果用那些已经在GitHub上有公开解答的题目——比如Codeforces的竞赛题——模型可能在训练时就已经见过，测出来的分数根本不算数。手写题目确保了评测的干净。

评测指标叫pass@k，意思是从模型生成的k个答案里，只要有一个能通过单元测试，就算这道题解出来了。这个指标的计算方式有一个技术细节值得一提：直接用通过率来估计pass@k会有很高的方差，所以论文用了一个无偏估计量，实际操作是每道题生成更多样本，然后用数学公式算出一个稳定的估计值，而不是简单地看"生成k个里有没有一个对的"。

讲完评测框架，再来讲模型本身。

Codex是用GPT家族的架构，在GitHub上抓取的公开Python代码上微调出来的。训练数据是2020年5月爬下来的五千四百万个公开仓库里的Python文件，过滤掉自动生成的、行太长的、字母数字比例太低的，最终留下大约159GB的代码。

这里有个有趣的发现：研究者本来以为从GPT-3开始微调会比从头训练好很多，因为GPT-3已经学会了理解自然语言，而docstring是自然语言写的，这应该有帮助。结果他们发现，从GPT-3微调和从头训练在最终性能上差别不大，可能是因为代码数据量已经足够大，模型能从代码本身学会语言理解。不过从GPT-3起步收敛更快，所以实际训练还是用了这个策略。

在分词器上也做了一个实用的优化：GPT-3原本的分词器不太适合处理代码，因为代码里有大量空白字符——缩进、对齐，这些东西用普通的分词方式会占用大量token，效率很低。研究团队专门给空白字符序列加了新token，结果代码的token数减少了大约30%，相当于同样的模型容量能处理更长的代码。

模型规模从85M参数到12B参数做了一系列，主要评测的是12B版本。

单次生成，也就是pass@1，12B参数的Codex解出了HumanEval里28.8%的题目。GPT-3在同样的题目上解出了0%，GPT-J这个六十亿参数的开源模型解出了11.4%。从零到28.8%，这个跨越背后的关键就是专门在代码上做的微调。

然后是那个让人印象深刻的发现：如果允许模型生成多个答案，性能会大幅提升。生成100个答案，选一个能通过测试的，pass@100达到了70.2%。这个结论乍听起来像是作弊，但它其实有非常实际的工程意义——在真实的开发工具里，你完全可以让模型多生成几个候选，然后自动跑单元测试来筛选，或者让用户看几个候选方案。更有意思的是，这里还涉及一个温度参数的选择：生成单个答案时，你希望模型比较保守，温度设低一点，大约0.2，结果会更确定；生成100个答案时，你希望多样性，温度设高一点，大约0.8，这样100个答案里覆盖到正确答案的概率更大。对不同的k值优化不同的温度，本身就是一个需要仔细设计的工程决策。

当然，实际部署时并不总是能跑单元测试来选答案。没有测试怎么办？论文发现，选平均对数概率最高的那个答案，比随机选要好，这个策略能把pass@1提升到大约44.5%。平均对数概率可以理解为模型对自己这个答案的"信心"，模型觉得最自然、最顺畅的那个生成，往往确实更有可能是对的。

论文还训练了一个进一步微调的版本，叫Codex-S。思路是这样的：GitHub上的Python代码什么都有，类定义、配置文件、数据文件，而HumanEval评测的是从docstring生成独立函数，这两个分布不太一样。所以研究团队专门收集了一批"有明确输入输出的独立函数"来做监督微调，数据来源有两个：一是编程竞赛网站上的题目，二是开源项目的持续集成测试——通过运行这些项目的集成测试，记录每个函数的实际输入输出，自动构造单元测试。

这些收集来的训练题也会过滤：让Codex-12B生成100个答案，如果一个都过不了测试，说明这道题要么太难要么表述不清，直接扔掉。

Codex-S的效果明显更好，pass@1比Codex高了平均6.5个百分点，pass@100高了15个百分点，12B参数的Codex-S在pass@100上达到了77.5%。

论文还做了一个反向实验：用相同的训练框架训练一个从代码生成docstring的模型，叫Codex-D。这个模型的应用场景之一是安全审计，因为如果能自动描述代码的意图，就能帮助人类判断生成的代码是不是在做你想让它做的事。Codex-D的表现和Codex-S大体相当，但有一些有趣的失败案例，比如模型生成的docstring有时候写的是"我在网上找到了这个函数"，或者"这个测试写得不对，也不是我的解法"，这些是训练数据里真实存在的人类注释，被模型学进去了，属于一种数据污染。

关于局限性，论文讲得很诚实。

最直接的一点是训练效率极低。Codex用了1590亿字节的代码来训练，而一个优秀的人类程序员一辈子能读的代码量远远不及这个数。论文里有一句话值得停下来想一想：一个刚学完入门计算机课的优秀学生，解题能力应该超过Codex-12B。这说明模型用了海量数据，却在推理泛化上仍然远不如人。

另一个具体的局限是对长操作链的处理。研究团队设计了一套由13个基本操作组成的合成测试，每个操作就是一个简单的字符串变换，比如转小写、删掉每第三个字符。他们把这些操作串联起来写成docstring，然后看模型能不能正确实现。结果是：随着操作数增加，模型的正确率呈指数下降。而一个人类程序员，只要能实现长度为2的操作链，理论上就能实现任意长度的，因为这是线性组合，没有额外的认知难度。模型在这里的表现是非线性退化，说明它在某种程度上是在做模式匹配，而不是真正理解了组合逻辑。

还有一个类似自然语言生成里常见的问题：属性绑定错误。当docstring里描述多个变量分别要做不同的操作时，模型经常会把操作对应到错误的变量上，特别是变量数量多的时候。论文里有一个具体例子，函数有四个参数x、y、z、w，docstring说要对y加3，对x和w减4，返回四个数的乘积，但模型生成的代码忘记对w减4，也没有正确计算乘积。

在更宏观的影响讨论上，论文花了相当篇幅。

过度依赖是个真实风险。Codex生成的代码看起来对，但可能有微妙的逻辑错误，新手程序员可能直接复制粘贴而不做验证。论文特别提到"自动化偏见"这个心理学概念，就是人们倾向于相信机器的输出，随着模型能力提升，这个问题会越来越严重。

安全漏洞是另一个关切。研究团队测试发现，Codex会生成包含已知安全漏洞的代码，比如使用不安全的加密算法。这不是模型故意的，而是训练数据里就有大量这样的代码，模型照着学了。

关于恶意使用，论文的立场比较审慎：他们认为以当前Codex的能力，并不会显著降低开发恶意软件的门槛，因为写恶意软件需要的不只是会写代码，还需要特定领域的知识和绕过防御的技巧。但他们也承认，模型的非确定性生成能力——每次生成的代码不同但功能相同——可能为多态恶意软件的开发提供便利，这是一个值得持续关注的威胁。

版权和法律问题也被提及。研究者发现，Codex生成的代码与训练数据完全相同的情况约占0.1%，而且这些情况通常是一些惯用写法反复出现，不太像是"背下来了"，更像是"学会了规律"。但这个领域的法律还在发展中，论文表示会持续关注。

整体来看，这篇论文的意义不只是"我们训练了一个会写代码的模型"。它给整个代码生成领域提供了一套可复现的评测框架——HumanEval后来成了这个领域的标准基准，pass@k也成了标准指标。它通过大量消融实验揭示了哪些训练策略真正有用，哪些是直觉上对但实际没什么差异的。它对局限性的分析也足够细致，没有停在泛泛的"模型还需要改进"，而是指出了具体在什么类型的推理上会失败，以及为什么。真正推动一个领域向前走的，往往不是最炫的结果，而是把评测标准定清楚、把失败模式讲明白，这件事Codex这篇论文做到了。
